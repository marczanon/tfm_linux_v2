\chapter{Implementación}

\section{Estructura del repositorio}

La implementación se organiza en tres áreas:

\begin{itemize}
  \item `codigo/`: aplicación, tests, datos, modelos, informes y documentación
        técnica;
  \item `memoria/`: documento LaTeX del TFM;
  \item `recursos/`: PDFs, referencias y diagramas auxiliares.
\end{itemize}

\section{Estado Actual}

Hasta este punto se ha creado la estructura inicial de directorios, se han
descargado los datasets crudos, se ha definido el flujo de datos del MVP y se
han implementado el contrato inicial del estado global del grafo y los esquemas
Pydantic de entradas, decisiones y resultados. Los datos crudos se conservan en
`codigo/data/raw/`, junto con un README de trazabilidad.

\section{Estado global implementado}

El estado global se ha dividido en dos capas:

\begin{itemize}
  \item `codigo/app/schemas/state.py`: modelos Pydantic estrictos para validar
        el estado, configuraciones, métricas, errores y artefactos;
  \item `codigo/app/graph/state.py`: `TypedDict` usado por LangGraph,
        validador de estado e inicializador del caso CWRU.
\end{itemize}

El inicializador `create\_initial\_cwru\_state` crea una ejecución preparada para
generar el manifiesto del dataset. El estado resultante no contiene señales ni
arrays, solo rutas, contexto experimental y campos reservados para artefactos
futuros.

\section{Contratos Pydantic implementados}

Se han añadido tres grupos de contratos:

\begin{itemize}
  \item `codigo/app/schemas/dataset.py`: manifiesto del dataset, canales y
        metadatos de fallo;
  \item `codigo/app/schemas/agent\_decisions.py`: decisiones estructuradas del
        supervisor, limpiador, estructurador, modelador, evaluador y redactor;
  \item `codigo/app/schemas/executor\_results.py`: resultados comunes y
        especializados de ejecutores deterministas.
\end{itemize}

Estos contratos consolidan la regla arquitectónica de que los agentes producen
configuraciones o decisiones validables, mientras que los ejecutores devuelven
rutas, métricas, errores y referencias a artefactos, pero no datos pesados.

\section{Adaptadores de Entrada}

Para reducir el acoplamiento al formato CWRU se ha introducido una capa ligera
de adaptadores en `codigo/app/services/signal\_adapters.py`. Esta capa expone
dos operaciones comunes: leer todos los canales numéricos de un fichero y cargar
un canal concreto como vector. Los ejecutores de perfilado y limpieza usan ahora
esta frontera en lugar de leer directamente ficheros `.mat`.

La implementación inicial soporta `.mat`, `.csv`, `.txt`, `.tsv` y `.npz`. En
el caso de CWRU, el adaptador reconoce los canales `DE\_time`, `FE\_time`,
`BA\_time` y `RPM`; en formatos tabulares, interpreta columnas numéricas como
canales. Para incorporar un nuevo origen, como NASA IMS, el objetivo será crear
o ampliar un adaptador de entrada y mantener estable el resto del pipeline:
perfilado, limpieza, estructuración, modelado y evaluación.

\section{Ejecutor de manifiesto}

Se ha implementado el primer ejecutor determinista del pipeline, el módulo
`dataset\_manifest.py`. Su responsabilidad es generar el artefacto:

\begin{center}
\begin{minipage}{0.85\textwidth}
\begin{verbatim}
codigo/data/interim/cwru_bearing/manifest.csv
\end{verbatim}
\end{minipage}
\end{center}

a partir de los ficheros `.mat` crudos de CWRU.

El ejecutor no carga señales completas. Solo inspecciona los nombres de fichero
y aplica un mapeo controlado de metadatos CWRU: carga, RPM, tipo de fallo,
diámetro y posición del fallo exterior cuando corresponde. El manifiesto
generado conserva la frecuencia original de cada fichero y fija una frecuencia
objetivo de 12 kHz para el MVP.

La ejecución real sobre los datos descargados ha generado 64 registros: 4
ficheros normales y 60 ficheros con fallo. El fichero resultante contiene 65
líneas incluyendo la cabecera.

\section{Ejecutor de perfilado}

Se ha implementado el perfilador determinista `data\_profiler.py`. Este ejecutor
lee el manifiesto, inspecciona los ficheros `.mat` y genera:

\begin{center}
\begin{minipage}{0.85\textwidth}
\begin{verbatim}
codigo/data/interim/cwru_bearing/profile.json
\end{verbatim}
\end{minipage}
\end{center}

El perfil contiene metadatos y estadísticas por canal: número de muestras,
valores no finitos, mínimo, máximo, media, desviación típica, RMS, curtosis y
energía. No almacena arrays ni señales completas.

La ejecución real ha perfilado 64 ficheros. El resumen agregado contiene 4
ficheros normales, 60 ficheros con fallo, frecuencias de muestreo de 48 kHz y
12 kHz, y los canales detectados `BA\_time`, `DE\_time`, `FE\_time` y `RPM`.

\section{Ejecutor de Limpieza}

Se ha implementado el ejecutor determinista `cleaning.py`. Este ejecutor lee el
manifiesto y el perfil, extrae el canal principal configurado, elimina valores
no finitos, remuestrea la señal a 12 kHz cuando procede y guarda una señal
limpia comprimida por fichero:

\begin{center}
\begin{minipage}{0.85\textwidth}
\begin{verbatim}
codigo/data/processed/cwru_bearing/clean_signals/
\end{verbatim}
\end{minipage}
\end{center}

También genera un resumen de auditoría en:

\begin{center}
\begin{minipage}{0.85\textwidth}
\begin{verbatim}
codigo/data/processed/cwru_bearing/cleaning_summary.json
\end{verbatim}
\end{minipage}
\end{center}

La ejecución real ha producido 64 ficheros `.npz` comprimidos. Los cuatro
ficheros normales se han remuestreado de 48 kHz a 12 kHz; los ficheros de fallo
ya estaban a 12 kHz. El estado del grafo conserva únicamente la ruta del
directorio limpio y las referencias a artefactos, no las señales.

\section{Ejecutor de Estructuración Temporal}

Se ha implementado el ejecutor determinista `structuring.py`. Este ejecutor lee
las señales limpias, valida que el canal y la frecuencia coincidan con la
configuración, genera ventanas temporales con tamaño 2048 y solapamiento del
50\%, calcula features temporales iniciales y crea particiones reproducibles a
nivel de fichero.

\begin{center}
\begin{minipage}{0.85\textwidth}
\begin{verbatim}
codigo/data/tensors/cwru_bearing/windows_features.csv
codigo/data/tensors/cwru_bearing/windows_raw.npz
codigo/data/tensors/cwru_bearing/splits.json
\end{verbatim}
\end{minipage}
\end{center}

La estrategia de partición evita mezclar ventanas de un mismo fichero entre
subconjuntos. Las ventanas normales se reparten entre entrenamiento,
validación y test, mientras que las ventanas con fallo se reservan para test.
La ejecución real ha generado 7460 ventanas de 2048 muestras: 175 de
entrenamiento, 117 de validación y 7168 de test. El tensor crudo tiene forma
`(7460, 2048)` y el directorio de tensores ocupa aproximadamente 22 MB.

\section{Ejecutor de Modelado Base}

Se ha implementado el ejecutor determinista `modeling.py` con el primer modelo
base de detección de anomalías: Isolation Forest. El modelo se entrena
únicamente con ventanas normales del subconjunto de entrenamiento y consume las
features temporales generadas por la fase anterior.

\begin{center}
\begin{minipage}{0.85\textwidth}
\begin{verbatim}
codigo/models/cwru_bearing/isolation_forest.joblib
codigo/models/cwru_bearing/predictions.csv
codigo/models/cwru_bearing/modeling_summary.json
\end{verbatim}
\end{minipage}
\end{center}

El artefacto `joblib` conserva el modelo entrenado, las columnas usadas y el
umbral de decisión. Las predicciones guardan, por cada ventana, identificador,
fichero original, partición, etiqueta real, puntuación de anomalía, umbral y
predicción binaria. Las métricas finales no se calculan en este ejecutor, sino
que se reservan para la fase de evaluación.

La ejecución real ha entrenado el modelo con 175 ventanas normales y ha
generado 7460 predicciones. El umbral estimado ha sido 0.5992 y el resumen de
modelado registra 398 ventanas predichas como normales y 7062 como anómalas.
Estos conteos son una salida preliminar del modelo, no una evaluación final de
rendimiento.

\section{Ejecutor de Evaluación}

Se ha implementado el ejecutor determinista `evaluation.py`. Este módulo lee las
predicciones del modelo, compara la etiqueta binaria real con la predicción de
anomalía y calcula métricas técnicas por partición. La partición principal para
el MVP es `test`.

\begin{center}
\begin{minipage}{0.85\textwidth}
\begin{verbatim}
codigo/reports/cwru_bearing/evaluation/metrics.json
codigo/reports/cwru_bearing/evaluation/evaluation_summary.md
\end{verbatim}
\end{minipage}
\end{center}

La ejecución real sobre el split de test ha obtenido precision 0.9991, recall
1.0000, F1-score 0.9996, ROC-AUC 1.0000, PR-AUC 1.0000 y una tasa de falsos
positivos de 0.0513. La matriz de confusión ha sido: 111 verdaderos negativos,
6 falsos positivos, 0 falsos negativos y 7051 verdaderos positivos.

Estos resultados deben interpretarse como validación del pipeline y del
baseline inicial sobre un benchmark controlado. No constituyen todavía una
garantía de generalización industrial, que se deberá analizar con validaciones
más exigentes y, posteriormente, con otros datasets como NASA IMS.

\section{Grafo LangGraph supervisado}

Se ha implementado el primer grafo LangGraph del MVP en `pipeline.py` y se ha
incorporado un supervisor en el modulo:

\begin{center}
\begin{minipage}{0.85\textwidth}
\begin{verbatim}
codigo/app/agents/supervisor.py
\end{verbatim}
\end{minipage}
\end{center}

La version actual ya contempla dos modos: un supervisor LLM que emite una
`SupervisorDecision` validada por Pydantic y una politica determinista de
respaldo para pruebas, ejecuciones locales sin modelo y recuperacion ante
respuestas invalidas.

El grafo ya no avanza directamente de un ejecutor al siguiente. Todas las
transiciones vuelven al supervisor:

\begin{center}
\begin{minipage}{0.85\textwidth}
\begin{verbatim}
START
-> supervisor
-> manifest_executor
-> supervisor
-> profiler_executor
-> supervisor
-> cleaner_agent
-> supervisor
-> cleaning_executor
-> supervisor
-> structuring_agent
-> supervisor
-> structuring_executor
-> supervisor
-> modeling_agent
-> supervisor
-> modeling_executor
-> supervisor
-> evaluator
-> supervisor
-> evaluation_agent
-> supervisor
-> report_writer
-> supervisor
-> END
\end{verbatim}
\end{minipage}
\end{center}

El grafo valida el estado entrante y saliente con `TFMStateModel`, registra
mensajes de trazabilidad, acumula referencias a artefactos y detiene la
ejecucion de forma controlada si un ejecutor devuelve estado `failed`. Cada
decision del supervisor se almacena en `messages` con rol `supervisor` y
contenido JSON serializado. El servicio LLM comun vive en:

\begin{center}
\begin{minipage}{0.85\textwidth}
\begin{verbatim}
codigo/app/services/llm.py
\end{verbatim}
\end{minipage}
\end{center}

La integracion inicial usa un cliente JSON para Ollama configurable por
variables de entorno. Si se activa `TFM\_SUPERVISOR\_MODE=llm`, el supervisor
solicita al modelo una decision estructurada; si no hay modelo disponible o la
respuesta no valida, se conserva la decision determinista como fallback.

Incluso cuando decide el LLM, la decision queda acotada por validaciones
posteriores: la fase actual debe coincidir con el estado real, no se aceptan
nodos fuera del plan del MVP, la revision humana permanece desactivada en esta
fase local y cualquier salto invalido fuerza el fallback. De este modo se
introduce toma de decisiones agentica sin permitir que el modelo ejecute codigo
ni manipule datos directamente.

\section{Agente Estructurador LLM}

Se ha implementado el agente estructurador LLM en:

\begin{center}
\begin{minipage}{0.85\textwidth}
\begin{verbatim}
codigo/app/agents/structurer.py
\end{verbatim}
\end{minipage}
\end{center}

Este agente decide la estructuracion temporal del dataset: tamano de ventana,
solapamiento, canal principal, frecuencia objetivo, modo de etiquetas, features
temporales y rutas esperadas de salida. Su salida principal es una
`StructuringDecision` validada por Pydantic. Igual que en el resto de fases, el
agente no genera ventanas ni tensores; la ejecucion real permanece en
`codigo/app/executors/structuring.py`.

La fase de estructuracion queda dividida en decision y ejecucion:

\begin{center}
\begin{minipage}{0.85\textwidth}
\begin{verbatim}
supervisor
-> structuring_agent
-> supervisor
-> structuring_executor
\end{verbatim}
\end{minipage}
\end{center}

Con `qwen3.5:4b`, el estructurador ha generado una decision valida con ventanas
de 2048 muestras, solapamiento del 50\%, canal `DE\_time`, frecuencia de 12 kHz,
modo `binary\_anomaly` y features temporales trazables como RMS, curtosis,
crest factor y energia.

En la Fase 3 se ha ampliado `StructuringDecision` con
`comparison\_candidates`. Este campo permite que el agente no solo proponga una
configuracion final, sino tambien alternativas comparables con su justificacion
y efecto esperado. La aplicacion no inventa esas alternativas: si el agente no
las devuelve, el plan comparativo no se construye.

Esta ampliacion se materializa en el script:

\begin{center}
\begin{minipage}{0.85\textwidth}
\begin{verbatim}
python -m codigo.scripts.run_cwru_agentic_window_comparison
\end{verbatim}
\end{minipage}
\end{center}

El script solicita a Qwen una decision de estructuracion con alternativas y,
solo despues, convierte esas propuestas en un plan experimental ejecutable con
el protocolo local. De este modo se conserva la separacion entre decision
agentica y ejecucion reproducible, pero se evita que una regla interna suplante
la deliberacion del agente.

Durante la integracion se ha detectado que `checkpoint\_id` es un nombre
reservado por LangGraph 1.1. Por ello se ha retirado de la vista `TypedDict`
que circula por el grafo. La persistencia futura debera apoyarse en los
checkpoints propios de LangGraph o en un campo de aplicacion que no colisione
con nombres reservados.

\section{Agente Modelador LLM}

Se ha implementado el agente modelador LLM en:

\begin{center}
\begin{minipage}{0.85\textwidth}
\begin{verbatim}
codigo/app/agents/modeler.py
\end{verbatim}
\end{minipage}
\end{center}

Este agente decide el modelo base y sus hiperparametros a partir del estado
ligero del pipeline, la configuracion de estructuracion y un resumen de la
tabla de features. Su salida principal es una `ModelingDecision` validada por
Pydantic. El agente no entrena modelos ni genera predicciones; la ejecucion
real se mantiene en `codigo/app/executors/modeling.py`.

La fase de modelado queda dividida en decision y ejecucion:

\begin{center}
\begin{minipage}{0.85\textwidth}
\begin{verbatim}
supervisor
-> modeling_agent
-> supervisor
-> modeling_executor
\end{verbatim}
\end{minipage}
\end{center}

Aunque el contrato `ModelingConfig` contempla algoritmos futuros como
One-Class SVM, LOF o autoencoders, la implementacion solo permite al agente
seleccionar modelos con ejecutor reproducible. Inicialmente se incluyo
`isolation\_forest`; en Fase 3 se ha anadido PCA con error de reconstruccion
como segundo modelo soportado. Tambien se acotan la semilla
(`random\_state = 42`), el split de entrenamiento (`train`), el uso del split de
validacion para el umbral y los hiperparametros permitidos, evitando que el LLM
seleccione opciones que la aplicacion aun no puede ejecutar de forma
reproducible.

Con `qwen3.5:4b`, el modelador ha generado una decision valida con
`model\_name = isolation\_forest`, `random\_state = 42`, entrenamiento sobre el
split `train`, validacion sobre `validation`, `n\_estimators = 200`,
`n\_jobs = 1` y `threshold\_quantile = 0.99`.

El contrato de decision del modelador incorpora ahora una lista de alternativas
comparables. Este campo permite que el agente proponga otros modelos o umbrales,
que despues se convierten en planes experimentales si estan soportados por el
ejecutor. Con ello se aumenta la capacidad de decision del agente sin permitir
modelos no implementados.

Durante esta validacion se ha ajustado el cliente de Ollama para usar
`think=false` por defecto en llamadas JSON estrictas, ya que este modelo puede
devolver el razonamiento en el campo `thinking` y dejar vacio
`message.content` si no se desactiva ese modo. Esta opcion no queda fijada de
forma rigida: puede activarse u omitirse mediante:

\begin{center}
\begin{minipage}{0.85\textwidth}
\begin{verbatim}
TFM_LLM_THINK=true
TFM_LLM_THINK=auto
\end{verbatim}
\end{minipage}
\end{center}

\section{Agente Evaluador LLM}

Se ha implementado el agente evaluador LLM en:

\begin{center}
\begin{minipage}{0.85\textwidth}
\begin{verbatim}
codigo/app/agents/evaluator.py
\end{verbatim}
\end{minipage}
\end{center}

Este agente interpreta las metricas calculadas por el ejecutor determinista de
evaluacion y devuelve una `EvaluationDecision` validada por Pydantic. La
separacion es deliberada: `codigo/app/executors/evaluation.py` calcula
precision, recall, F1, ROC-AUC, PR-AUC, tasa de falsos positivos y matriz de
confusion; el agente solo emite el juicio tecnico, la aprobacion y las
limitaciones del experimento.

La fase de evaluacion queda dividida en calculo y juicio agentico:

\begin{center}
\begin{minipage}{0.85\textwidth}
\begin{verbatim}
supervisor
-> evaluator
-> supervisor
-> evaluation_agent
-> supervisor
\end{verbatim}
\end{minipage}
\end{center}

Para el MVP CWRU se han fijado umbrales conservadores y explicitos:

\begin{center}
\begin{minipage}{0.85\textwidth}
\begin{verbatim}
min_recall_required = 0.90
max_false_positive_rate = 0.10
\end{verbatim}
\end{minipage}
\end{center}

El LLM puede redactar el resumen tecnico y las limitaciones, pero no puede
aprobar una ejecucion que incumpla esos umbrales. Si la respuesta no valida o
contradice las metricas, se activa un fallback determinista.

Tras esta decision, el supervisor no interpreta una metrica baja como fallo de
infraestructura. Si existen metricas, enruta la fase final hacia el agente
redactor y el informe se genera igualmente. La aprobacion experimental queda
codificada en `evaluation.approved`: una run puede terminar como `completed` y
al mismo tiempo quedar `approved=false` con limitaciones explicitas. El estado
`failed` se reserva para errores de contratos, artefactos o ejecutores. El
fichero de metricas se genera en:

\begin{center}
\begin{minipage}{0.85\textwidth}
\begin{verbatim}
codigo/reports/cwru_bearing/evaluation/metrics.json
\end{verbatim}
\end{minipage}
\end{center}

`report`. Con ello el pipeline cierra el ciclo completo del MVP: datos crudos,
perfilado, limpieza, estructuracion, modelado, evaluacion, juicio agentico e
informe tecnico trazable.

\section{Persistencia Local de Ejecuciones}

Como primer hito de la segunda fase se ha implementado una persistencia local
de ejecuciones en:

\begin{center}
\begin{minipage}{0.85\textwidth}
\begin{verbatim}
codigo/app/services/run_persistence.py
\end{verbatim}
\end{minipage}
\end{center}

El objetivo es conservar una evidencia ligera y auditable de cada ejecucion sin
introducir todavia una base de datos externa. El servicio recibe un
`TFMStateModel` final y genera una carpeta por `run\_id` con el estado final,
las decisiones extraidas de los mensajes del grafo, los artefactos, las
metricas, la evaluacion, un resumen Markdown y una metadata del snapshot.

\begin{center}
\begin{minipage}{0.85\textwidth}
\begin{verbatim}

codigo/reports/runs/<run_id>/decisions.json
codigo/reports/runs/<run_id>/artifacts.json
codigo/reports/runs/<run_id>/metrics.json
codigo/reports/runs/<run_id>/evaluation.json
codigo/reports/runs/<run_id>/summary.md
codigo/reports/runs/<run_id>/snapshot.json
\end{verbatim}
\end{minipage}
\end{center}

Ademas, se mantiene un indice local:

\begin{center}
\begin{minipage}{0.85\textwidth}
\begin{verbatim}
codigo/reports/runs/index.json
\end{verbatim}
\end{minipage}
\end{center}

Esta decision mantiene separado el pipeline puro de la persistencia. La funcion
`run\_cwru\_pipeline` no se modifica; la integracion automatica se realiza
mediante un wrapper de ejecucion persistida. De este modo se conserva la
estabilidad del grafo ya validado y se prepara la comparacion de ejecuciones
para los experimentos de la Fase 2.

\section{Wrapper de Ejecucion Persistida}

\section{Registro Consultable de Ejecuciones}

El tercer hito de la Fase 2 introduce una capa de consulta sobre las ejecuciones

\begin{center}

\end{verbatim}
\end{minipage}
\end{center}

Este servicio lee el indice local de ejecuciones y los snapshots generados por

consulta evidencia ya persistida. Esta separacion prepara la futura API minima,
que podra exponer consultas sobre ejecuciones sin acoplarse a LangGraph ni a
los ejecutores.

\section{Contratos Iniciales Multi-Dataset}

Como primer paso de la Fase 3 se han incorporado contratos comunes para
desacoplar el pipeline del caso CWRU sin modificar todavia los ejecutores ya
validados. En `codigo/app/schemas/dataset.py` se han añadido
`DatasetDescriptor`, `DatasetAdapterInfo` y `CommonManifestRecord`. Estos
modelos permiten describir datasets heterogeneos, registrar adaptadores y
representar filas de manifiesto comunes sin almacenar senales completas.

Tambien se ha creado el servicio `codigo/app/services/dataset\_adapters.py`,
que expone un registro local de adaptadores. La primera version incluye
adaptadores para CWRU, NASA IMS y senales tabulares genericas. Esta capa solo
inspecciona rutas y cabeceras ligeras; no modifica datos crudos ni lanza
transformaciones costosas.

La decision mantiene el flujo CWRU existente como benchmark de regresion. El
adaptador `cwru\_bearing` se ha integrado como envoltorio del manifiesto actual
mediante una funcion comun de generacion de manifiestos, delegando internamente
en el ejecutor CWRU ya verificado. Los tests comprueban que el CSV generado por
esta ruta comun coincide con el manifiesto producido por la ruta historica.

Para NASA IMS, el adaptador reconoce rutas o ficheros con patron temporal
compatible, infiere canales desde ficheros sinteticos pequenos y registra
advertencias cuando detecta recuentos de canales inconsistentes. Tras la
inspeccion local, se ha implementado `build\_manifest(...)` solo para carpetas
preextraidas. Esta funcion genera un manifiesto comun con una fila por snapshot,
`label = unknown`, fallo final conocido a nivel de set, frecuencia de 20 kHz,
canales serializados como JSON y metadatos escalares sobre puntos por fichero,
duracion nominal, carga, regimen y variante local.

La inspeccion local ha confirmado que el paquete disponible se organiza como
`zip -> 7z -> rar`, con tres archivos RAR de experimentos y un README interno.
El README describe tres ensayos test-to-failure con snapshots ASCII de un
segundo, 20.480 puntos por fichero y frecuencia de muestreo de 20 kHz. Tambien
se ha detectado una discrepancia local en el tercer RAR, que lista mas ficheros
y una ruta interna distinta a la descrita por el README. Por ello, la primera
implementacion de manifiesto NASA IMS trabaja con carpetas preextraidas y
sinteticas antes de procesar el paquete completo. La ingestion directa del
contenedor anidado queda pospuesta hasta decidir dependencias y experiencia de
interfaz.

El perfilador `data\_profiler.py` se ha generalizado para detectar si el CSV de
entrada sigue el formato historico CWRU o el contrato comun. Para NASA IMS,
propaga `record\_id`, `run\_id`, `condition\_id`, `primary\_channel`, canales
de manifiesto y metadatos JSON. La capa `signal\_adapters.py` tambien reconoce
ficheros IMS con nombre temporal y sin extension, expone `read\_signal\_frame`
para leerlos como tablas numericas con `pandas` y asigna canales normalizados
`channel\_1`, `channel\_2`, etc. Esta adaptacion permite generar perfiles
estadisticos sobre estructuras NASA preextraidas.

El perfil incluye ademas un bloque `decision\_summary` orientado al agente
limpiador. Este bloque clasifica si el perfil esta limpio, requiere remuestreo,
requiere seleccionar canal o presenta calidad insuficiente. Tambien enumera
acciones requeridas, canales candidatos, opciones de limpieza soportadas y
advertencias bloqueantes o no bloqueantes. De este modo, el LLM local no
necesita conocer de memoria el dataset industrial: recibe un expediente experto
calculado por el sistema y decide dentro de un espacio de accion validado.

El ejecutor `cleaning.py` tambien se ha generalizado para consumir manifiestos
comunes. El contrato `CleaningConfig` incorpora `selected\_channel`; si se
declara, el ejecutor carga ese canal mediante la capa de adaptadores de senal y
lo valida contra `channel\_names` en los manifiestos comunes. Si no se declara,
mantiene compatibilidad con `sensor\_channel` para CWRU y con
`primary\_channel` para NASA IMS. La salida `.npz` conserva metadatos ligeros
como `record\_id`, `dataset`, `run\_id`, `condition\_id` y `label\_detail`,
manteniendo la estructura comun necesaria para estructuracion posterior.

El ejecutor `structuring.py` incorpora un resumen experto para el agente
estructurador. A partir de las señales limpias estima configuraciones
soportadas de ventana y solape, numero aproximado de ventanas, coste relativo,
conjuntos de features temporales disponibles y advertencias de fuga de
informacion por fichero, run o secuencia temporal. El agente puede elegir entre
estas configuraciones, pero la validacion mantiene los valores dentro de rangos
controlados y las features dentro de las implementadas por el ejecutor.

\section{Bucle de Reintento Agentico}

Para convertir una ejecucion rechazada en aprendizaje trazable se ha añadido
un servicio de analisis de fallo y un contrato especifico de reintento:

\begin{center}
\begin{minipage}{0.95\textwidth}
\footnotesize
\begin{verbatim}
codigo/app/services/iteration_analysis.py
codigo/scripts/run_nasa_ims_agentic_retry.py
ModelingRetryDecision
\end{verbatim}
\end{minipage}
\end{center}

El servicio `iteration\_analysis.py` resume la ejecucion fallida sin exponer el
dataset completo al LLM: calcula matriz de confusion, falsos negativos, falsos
positivos, estadisticos de puntuacion, umbral efectivo y reintentos restantes.
El agente modelador recibe ese expediente y debe devolver JSON validable con
`should\_retry`, `retry\_config`, `learning\_summary`, `expected\_effect` y
`stop\_reason` cuando decida parar.

La logica de ejecucion sigue siendo determinista. El agente no entrena modelos
ni modifica predicciones; solo propone una nueva `ModelingConfig` soportada. El
script ejecuta como maximo dos intentos, persiste cada decision y, si el ultimo
intento sigue rechazado, fuerza `next\_action = stop` en la evaluacion efectiva
para impedir bucles infinitos. Esta parada no sustituye al juicio del agente:
documenta el limite operativo pactado para la ejecucion.

Para auditar si el agente razono de forma consistente, se ha añadido una capa
de post-mortem:

\begin{center}
\begin{minipage}{0.95\textwidth}
\footnotesize
\begin{verbatim}
codigo/app/services/reasoning_audit.py
codigo/app/schemas/reasoning.py
codigo/scripts/create_agentic_reasoning_audit.py
\end{verbatim}
\end{minipage}
\end{center}

El post-mortem compara hipotesis, evidencia, accion, efecto esperado y metricas
antes/despues. Ademas puede generar una solicitud de revision humana y una
plantilla JSON de veredicto. Esta revision humana no altera la ejecucion; sirve
para decidir si el razonamiento debe reutilizarse como contexto, descartarse o
tratarse como caso frontera.

Como inicio de la Fase 4 se han añadido los contratos de memoria agentica
supervisada. Estos contratos no implementan todavia una base vectorial, pero
fijan la semantica que debera cumplir el futuro RAG: `HumanReviewSettings`
mantiene Human-in-the-loop apagado por defecto, `ReasoningMemoryRecord`
distingue ejemplos positivos, negativos, advertencias y casos frontera, y
`RetrievedMemoryContext` valida que el contexto recuperado pertenece al agente
consultado. Un razonamiento `overcorrected` o `unsafe` no puede convertirse en
ejemplo positivo; como mucho puede reutilizarse como advertencia o caso
frontera si la politica de revision humana lo permite.

Sobre esos contratos se ha implementado el primer backend local de memoria
vectorial. `LocalHashEmbeddingModel` genera embeddings deterministas por
hashing y `LocalJsonVectorMemoryStore` persiste colecciones por agente en JSON,
calcula similitud coseno y devuelve un `RetrievedMemoryContext` validado. Esta
eleccion evita dependencias externas en el primer hito de Fase 4 y permite
probar la semantica de RAG antes de adoptar una base vectorial mas especializada
como FAISS o Chroma. La memoria queda acotada por agente: una consulta del
modelador puede recuperar `modeler\_memory` y memoria metodologica compartida,
pero no recuerdos propios del limpiador.

Para uso real se ha definido un proveedor `OllamaEmbeddingProvider`, que llama
a `/api/embed` y registra modelo, version y dimension del vector en cada
recuerdo. El modelo por defecto seleccionado es `qwen3-embedding:0.6b`, por su
equilibrio entre coherencia con los agentes Qwen, tamano moderado, soporte
multilingue y ventana de contexto amplia. El proveedor determinista por hashing
queda reservado para tests y reconstrucciones sin dependencia externa; la
memoria operacional debe reconstruirse si se cambia de modelo de embeddings, ya
que los vectores de modelos distintos no comparten necesariamente el mismo
espacio semantico.

Para convertir los razonamientos auditados en memoria se ha anadido un servicio
de indexacion y un comando de reconstruccion reproducible. El indexador recorre
los post-mortems persistidos, busca una revision final humana junto al artefacto
original y, por defecto, solo indexa recuerdos reutilizables cuando existe dicha
validacion humana. Esta politica mantiene el modo Human-in-the-loop apagado
para la ejecucion normal, pero exige revision cuando se desea alimentar la
memoria agentica. Los post-mortems sin revision quedan registrados como
pendientes; si se activa una opcion explicita de inclusion, solo pueden entrar
como advertencia o caso frontera, no como ejemplo positivo. El modelo
`qwen3-embedding:0.6b` se ha instalado en Ollama y se ha verificado con una
llamada real a `/api/embed`, obteniendo vectores de dimension 1024 para la
memoria operacional.

El reintento agentico del modelador ya puede recibir memoria de forma opcional.
El contrato `ModelingRetryDecision` declara ahora si el agente uso memoria
recuperada, el identificador del contexto consultado y los recuerdos concretos
citados. Durante la construccion del prompt se genera una consulta
`AgentMemoryQuery` para `modeler\_memory`, se recuperan hasta tres recuerdos y
se pasan al agente como contexto compacto con similitud, veredicto humano,
resumen, metricas y ruta de origen. La validacion posterior rechaza cualquier
decision que cite un recuerdo no recuperado, por lo que el agente conserva
libertad argumentativa pero no puede inventar memoria. Esta funcionalidad queda
apagada por defecto; el script de reintento la activa solo con una opcion
explicita y persiste el contexto en `retrieved\_memory\_context.json`.

Para aumentar la evidencia de investigacion, el contrato del modelador exige
ahora una declaracion mas detallada cuando usa memoria: resumen de uso, tipo de
relacion con cada recuerdo (`followed`, `adapted`, `contradicted` o `ignored`),
influencia concreta y mitigacion del riesgo si el recuerdo era un caso frontera
o una advertencia. Sobre esa declaracion se ha implementado
`memory\_usage\_audit.py`, que compara lo que el agente dijo hacer con la
memoria recuperada y las metricas finales. La auditoria genera
`memory\_usage\_audit.json` y `memory\_usage\_audit.md`, y puede clasificar una
decision como `memory\_repeated\_boundary\_failure` si el agente cita un caso
frontera pero repite el mismo tipo de fallo experimental.

El aprendizaje por memoria se ha generalizado para no depender solo del agente
modelador ni de post-mortems finales. El tipo de fuente
`memory\_usage\_audit` permite transformar una auditoria de uso de memoria en
un nuevo `ReasoningMemoryRecord`. La conversion recibe explicitamente el
`target\_agent`, de modo que el mismo mecanismo puede alimentar
`cleaner\_memory`, `structurer\_memory`, `evaluator\_memory`,
`report\_writer\_memory`, `researcher\_memory` o
`shared\_methodology\_memory`. En el caso actual, la auditoria donde el
modelador cito un recuerdo de frontera pero repitio FPR 1.0 se incorpora como
`warning`, no como ejemplo positivo.

Como primera carga canonica de memoria, se ha revisado el post-mortem del
segundo reintento NASA sintetico. El veredicto humano registrado es
`partially\_correct`: la decision del agente acerto la direccion del cambio al
reducir falsos negativos, pero sobrecorrigio la magnitud del umbral y elevo la
tasa de falsos positivos hasta 1.0. El caso queda por tanto como
`boundary\_case`, reutilizable como advertencia para el modelador, no como
ejemplo positivo. Al reconstruir la memoria con `qwen3-embedding:0.6b`, se ha
generado un vector de dimension 1024 en `modeler\_memory`; el informe de
indexacion conserva ademas que otro post-mortem sigue pendiente de revision
final. Una consulta de humo sobre sobrecorreccion de umbral recupera este
recuerdo como `boundary\_context` con una similitud aproximada de 0.6868.

Tras incorporar las auditorias de uso como fuente opcional, se reconstruyo la
memoria canonica con `--include-memory-usage-audits`. El indice contiene ahora
dos recuerdos: el post-mortem revisado por humano como `boundary\_case` y la
auditoria de uso como `warning`. Una consulta de humo sobre repeticion de fallo
por umbral recupera primero la advertencia derivada de la auditoria
(`negative\_warning`, similitud aproximada 0.6852) y despues el caso frontera
revisado (`boundary\_context`, similitud aproximada 0.6559). Esto cierra un
primer ciclo de aprendizaje controlado: revision humana, memoria de frontera,
uso agentico, auditoria del uso y nueva memoria de advertencia.

Para que esta memoria no quede limitada a parametros concretos, se ha
introducido un contrato general de episodios de decision. `DecisionEpisode`
describe una decision agentica completa: agente, tipo de decision, contexto,
alternativas consideradas, accion elegida, efecto esperado, evidencia usada,
resultado de ejecucion, metricas antes/despues, trade-offs observados, modos de
fallo, leccion aprendida y condiciones de reutilizacion. Este contrato sirve
tanto para el modelador como para el limpiador, estructurador, evaluador,
redactor o futuro investigador.

Sobre el episodio se define `MemoryCandidate`, que es la version destilada y
lista para RAG. Un candidato debe indicar `target\_agent`, `memory\_role`,
`when\_to\_reuse`, `when\_not\_to\_reuse` y `risk\_if\_misused`. La politica de
seguridad se mantiene: un ejemplo positivo requiere veredicto humano correcto,
un candidato reutilizable debe declarar cuando se puede usar, y una advertencia
o ejemplo negativo debe aportar condiciones de no reutilizacion o riesgo. El
indexador de memoria recoge automaticamente `memory\_candidate.json` y lo
convierte en `ReasoningMemoryRecord`, generando despues el embedding local y
almacenandolo en la coleccion vectorial del agente correspondiente.

El contrato anterior ya se ha conectado al flujo real de reintentos. El servicio
`decision\_memory.py` transforma el post-mortem del modelador en
`decision\_episode.json` y `memory\_candidate.json`, junto con sus versiones
Markdown. El episodio conserva la configuracion elegida como alternativa
seleccionada, las alternativas comparables si existen, los recuerdos
recuperados, la evaluacion final, los trade-offs y las condiciones de
reutilizacion. El candidato queda marcado como reutilizable cuando no existe
una revision humana bloqueante; si se solicita revision, se conserva como
evidencia pero no debe incorporarse automaticamente al contexto recuperable
hasta recibir validacion.

Para que estos episodios influyan en decisiones mas amplias que un simple
ajuste de umbral, el prompt de reintento del modelador expone ahora el
`source\_type` de cada recuerdo recuperado y reconoce etiquetas de comparacion
de familia de modelo tras una mejora parcial. Cuando aparece este tipo de
memoria, el agente recibe una instruccion explicita de considerar familias de
modelo soportadas, no solo mover `threshold\_quantile`. El formato esperado de
`ModelingRetryDecision` incluye tambien candidatos comparables, por ejemplo una
alternativa PCA y otra variante moderada de Isolation Forest. Estos candidatos
no se ejecutan de forma automatica; documentan la deliberacion del agente,
mientras que la ejecucion real sigue limitada a una unica `retry\_config`
validada.

La auditoria de uso de memoria se ha ampliado con una comprobacion de
coherencia del razonamiento. Ademas de detectar repeticiones de fallos de
frontera, ahora puede clasificar una decision como
`memory\_reasoning\_inconsistent` cuando la explicacion del agente contiene una
comparacion numerica imposible, por ejemplo afirmar que `0.95` es mayor que
`0.99`, o cuando describe un cuantil `0.99` como bajo. Esta comprobacion no
cambia la decision del agente ni las metricas, pero deja evidencia trazable de
errores en su razonamiento declarado. La auditoria resultante puede
incorporarse posteriormente a `modeler\_memory` como `warning`, de forma que el
siguiente agente vea no solo el resultado experimental, sino tambien la
calidad de la explicacion usada para llegar a el.

Para transformar la comparacion de familia en una accion ejecutable, se ha
anadido ademas una guia derivada de memoria al prompt del modelador. Esta guia,
`memory\_retry\_guidance`, resume si los recuerdos recuperados indican que los
ajustes de umbral sobre Isolation Forest ya han producido solo mejoras
parciales rechazadas. En ese caso marca como preferente una configuracion
`pca\_reconstruction\_error` y advierte que no debe repetirse otro reintento
basado solo en `threshold\_quantile` de Isolation Forest. La guia no ejecuta
nada por si misma: sigue siendo el agente quien debe devolver `retry\_config` o
`should\_retry=false`, y la decision vuelve a pasar por los contratos Pydantic.
La primera ejecucion real con esta guia consiguio que Qwen eligiera PCA como
modelo ejecutado.

Tras obtener esta evidencia, la implementacion se ha reorientado para no
concentrar la Fase 4 en ajustes de umbral o en una unica familia de modelos. El
servicio `agent\_memory.py` centraliza ahora la preparacion de memoria recuperada
para prompts, la plantilla comun de declaracion de uso y la validacion de que
un agente solo cite recuerdos realmente recuperados. Sobre esta base,
`StructuringDecision` y `EvaluationDecision` incorporan los mismos campos de
memoria que el reintento del modelador: contexto recuperado, recuerdos citados,
resumen de uso y declaracion por recuerdo.

El agente estructurador dispone de `build\_structurer\_memory\_query` y
`retrieve\_structurer\_memory\_context`, orientados a recuperar experiencias
sobre ventanas, solape, features, frecuencia de muestreo y particion temporal.
La memoria se inyecta en el prompt como contexto historico, pero la validacion
sigue impidiendo ventanas, canales, solapes o features no soportadas. De forma
analoga, el agente evaluador dispone de `build\_evaluator\_memory\_query` y
`retrieve\_evaluator\_memory\_context`; sus recuerdos pueden mejorar la
explicacion y las limitaciones, pero no pueden aprobar metricas que incumplen
el protocolo local.

Tambien se han ampliado los episodios de decision para estos dos agentes.
`decision\_memory.py` puede construir episodios y candidatos de memoria para
`structurer\_memory` y `evaluator\_memory`, no solo para `modeler\_memory`.
Esto convierte la memoria en un mecanismo transversal de aprendizaje gradual:
cada ejecucion futura podra dejar evidencia sobre decisiones de estructuracion,
juicios de evaluacion y condiciones de reutilizacion, sin forzar errores
artificiales ni depender exclusivamente del ajuste de hiperparametros.

La preparacion anterior se ha conectado despues al grafo completo mediante
`PipelineMemoryConfig`. Cuando se activa un `VectorMemoryStore`, el nodo del
estructurador y el nodo del evaluador recuperan memoria de su propia coleccion,
persisten el contexto recuperado bajo una ruta agentica de la ejecucion y lo
pasan al agente antes de validar su decision:

\begin{center}
\begin{minipage}{0.95\textwidth}
\footnotesize
\begin{verbatim}
codigo/reports/<dataset>/<run_id>/agent_memory/<agent>/
  retrieved_memory_context.json
  decision_episode.json
  decision_episode.md
  memory_candidate.json
  memory_candidate.md
\end{verbatim}
\end{minipage}
\end{center}

La configuracion queda apagada por defecto, de modo que las pruebas canonicas y
el pipeline historico conservan el mismo comportamiento si no se proporciona
memoria.

Para cerrar el circuito operacional se ha añadido un script especifico:

\begin{center}
\begin{minipage}{0.8\textwidth}
\footnotesize
\begin{verbatim}
codigo/scripts/run_cwru_pipeline_with_memory.py
\end{verbatim}
\end{minipage}
\end{center}

Este script ejecuta el pipeline CWRU persistido con `PipelineMemoryConfig`,
permite elegir proveedor de embeddings, puede activar Qwen con `--use-llm` y
reconstruye el indice RAG al finalizar si se usa `--rebuild-index`. Es
deliberadamente especifico de CWRU: no selecciona entre CWRU y NASA IMS, sino
que crea el estado con `create\_initial\_cwru\_state` y usa los ejecutores CWRU
por defecto. Para NASA IMS se mantienen scripts separados, porque la politica
temporal y los guardarrailes metodologicos son distintos. Ademas, el script
rechaza rutas `--raw-path` que parezcan NASA/IMS para evitar una ejecucion mal
etiquetada. En una primera run determinista se generaron los primeros
candidatos de `structurer\_memory` y `evaluator\_memory`; en una segunda run
con Qwen, ambos agentes recuperaron esos recuerdos y declararon
`used\_memory\_context=true`. El indice resultante contiene veinte registros:
dieciseis del modelador, dos del estructurador y dos del evaluador.

Tras esa ejecucion se ha incorporado una auditoria cualitativa transversal en
`transversal\_memory\_audit.py`, expuesta mediante
`audit\_transversal\_memory\_run.py`. Esta auditoria no recalcula metricas ni
modifica la decision; comprueba que los recuerdos citados fueron recuperados,
que cada recuerdo citado tiene declaracion `memory\_record\_uses`, que el
dataset y el agente coinciden, y que el evaluador mantiene respaldo metrico
actual. En la run `cwru-memory-transversal-fase4-002-llm` el resultado fue
`memory\_aligned` para estructurador y evaluador. Los candidatos generados
pueden reutilizarse como contexto, pero quedan marcados como necesitados de
revision humana antes de usarse como evidencia academica principal.

Para anticipar una futura interfaz de seleccion de dataset, se ha añadido una
capa comun de planificacion multi-dataset:

\begin{center}
\begin{minipage}{0.9\textwidth}
\footnotesize
\begin{verbatim}
codigo/app/schemas/pipeline_run.py
codigo/app/services/pipeline_runner.py
codigo/scripts/run_dataset_pipeline_with_memory.py
\end{verbatim}
\end{minipage}
\end{center}

La interfaz prevista no deberia llamar directamente a scripts especificos
`cwru\_*` o `nasa\_*`. Debe construir un `PipelineRunRequest`, resolver el
adaptador registrado, generar un `DatasetPipelinePlan` y mostrar la politica de
capacidades antes de ejecutar. CWRU permite el pipeline supervisado completo.
NASA IMS real permite manifiesto, perfilado, limpieza y estructuracion, pero
bloquea modelado y evaluacion supervisados mientras no exista una politica
temporal y de etiquetas defendible. Si NASA IMS se usa como benchmark sintetico
controlado, la peticion debe declararlo mediante `allow\_synthetic\_labels`.
Si se desea ejecutar NASA IMS como secuencia run-to-failure con etiquetas proxy,
la peticion debe declarar una politica versionada mediante
`dataset\_policy\_id`. La primera politica implementada es
`nasa\_ims\_temporal\_v1`, documentada en
`codigo/docs/33\_politica\_temporal\_nasa\_ims.md`.
Los nombres historicos del grafo se mantienen por compatibilidad, pero se han
añadido alias neutrales (`run\_pipeline`, `run\_and\_persist\_pipeline`) para
evitar acoplar la futura API al nombre CWRU.

La politica `nasa\_ims\_temporal\_v1` se aplica despues de generar el
manifiesto comun NASA IMS y antes del perfilado. El servicio
`nasa\_ims\_temporal\_policy.py` escribe un nuevo manifiesto derivado,
`manifest\_temporal\_policy\_v1.csv`, conserva el manifiesto original y marca
cada registro con `label\_source=temporal\_proxy\_v1` y
`official\_nasa\_labels=false`. El tramo inicial de cada `run\_id` se etiqueta
como `normal`, el tramo posterior como `degradation` y `metadata\_json` incluye
`split\_hint`, `split\_source`, `temporal\_order\_index` y
`temporal\_phase`. La estructuracion temporal reconoce estos `split\_hint`
solo cuando todos los registros limpios los declaran; en caso contrario,
mantiene la estrategia historica por etiquetas normales/fallo. Asi, CWRU no
cambia y NASA IMS no depende de una inferencia implicita dentro del ejecutor.

Como pulido adicional de trazabilidad multi-dataset, los artefactos comunes ya
no usan nombres internos heredados de CWRU cuando se ejecutan sobre NASA IMS.
Las rutas pueden seguir apuntando a `cwru\_bearing` en el benchmark historico,
pero los identificadores de artefacto pasan a ser neutrales:
`windows\_features`, `model\_predictions`, `modeling\_summary`,
`evaluation\_metrics` y `evaluation\_summary`. Esto reduce el acoplamiento
visual del sistema a CWRU y hace mas clara la lectura de snapshots
multi-dataset.

\section{API Controlada de Ejecucion}

Tras consolidar el runner comun, se ha iniciado el Hito 8 de Fase 4 con una
primera version de `POST /runs`. La API conserva los endpoints de lectura sobre
runs persistidos y anade un contrato especifico:

\begin{center}
\begin{minipage}{0.9\textwidth}
\footnotesize
\begin{verbatim}
codigo/app/schemas/api_runs.py
codigo/app/services/api_run_jobs.py
codigo/app/api/routes.py
\end{verbatim}
\end{minipage}
\end{center}

La solicitud de ejecucion API extiende el contrato multi-dataset con el campo
`dry\_run`, que por defecto vale `true`. En ese modo, la API no ejecuta el
pipeline: construye un plan de ejecucion y devuelve si las fases solicitadas
estan permitidas, que adaptador se usara, que rutas se derivan y que bloqueos
existen. Si el cliente envia `dry\_run=false`, la API intenta ejecutar el runner
comun, pero solo despues de aplicar guardarrailes.

Los guardarrailes iniciales son deliberadamente conservadores. `raw\_path` debe
estar dentro de una raiz permitida por `create\_app`, siendo `codigo/data/raw`
la raiz por defecto. La ejecucion falla con respuesta HTTP `409` si la politica
multi-dataset bloquea modelado o evaluacion. Ademas, esta primera version no
permite ejecutar con `use\_llm=true` ni con memoria RAG desde API; esas
capacidades se reservaran para una politica posterior con Human-in-the-loop,
coste y auditoria mas explicitos. Finalmente, si el `run\_id` ya existe en el
registro local, la API responde `409` para evitar sobrescrituras accidentales.

La primera pieza de Human-in-the-loop se ha conectado a esta puerta de API sin
crear contratos duplicados. La solicitud reutiliza los contratos de revision ya
existentes y la logica comun se centraliza en un servicio dedicado. En modo
`off` no interviene; en modo `passive` devuelve razones de revision sin
bloquear; en modo `required` impide ejecutar salvo que llegue una aprobacion
explicita. Cuando la aprobacion existe, se inserta en el estado inicial y queda
persistida en el snapshot de la run. Esta implementacion cubre la puerta minima
de revision, pero no introduce todavia colas, usuarios, notificaciones ni una
interfaz de aprobacion completa.

La respuesta `ApiRunResponse` devuelve siempre el plan y, cuando hay ejecucion,
tambien el snapshot persistido, la fase final, el estado `approved`, la ruta del
informe, las metricas y los errores. Esto permite que una interfaz futura
distinga entre ejecucion tecnica completada y resultado experimental no
aprobado por metricas.

Como siguiente paso incremental se ha anadido una ejecucion en segundo plano
local, activada mediante `background=true` junto con `dry\_run=false`. Esta
opcion no introduce un segundo runner: el job invoca el runner comun y conserva
la persistencia de snapshots como fuente de verdad cuando la ejecucion termina.
El estado intermedio se mantiene en memoria del proceso mediante un registro de
jobs y se consulta con un endpoint especifico. Por tanto, esta ampliacion sirve
para una futura UI local, pero no pretende ser todavia una cola persistida con
workers externos, cancelacion o tolerancia a reinicios.

\section{Siguiente Paso de Implementación}

Con la Fase 4 cerrada, el siguiente bloque de trabajo pasa a ser la aplicacion
local completa. La nueva Fase 5 tendra como objetivo construir una interfaz
backend/frontend capaz de seleccionar o recibir datasets, ejecutar runs mediante
la API controlada, seguir jobs en segundo plano, visualizar metricas, informes y
artefactos, y consultar la memoria local generada por los agentes. Esta fase
mantendra las mismas reglas metodologicas: reutilizacion de componentes
existentes, documentacion tecnica paralela y actualizacion de la memoria
academica.

Como primer avance de esta fase se ha creado un esqueleto de frontend local en
React, TypeScript y Vite. La pantalla inicial consulta el estado de la API,
lista las ejecuciones persistidas y permite enviar una solicitud `POST /runs`
con `dry\_run=true`, mostrando el plan devuelto por el backend sin ejecutar el
pipeline. Esta decision mantiene la logica de planificacion y las politicas de
dataset en FastAPI y en los servicios Python existentes, evitando duplicar
contratos en la interfaz. La verificacion incluyo la compilacion del frontend y
una prueba HTTP del proxy local hacia `GET /health` y `POST /runs`.

El segundo avance de Fase 5 sustituye el catalogo local de la interfaz por una
consulta al backend. Se han incorporado los endpoints `GET
/datasets/adapters` y `POST /datasets/describe`, ambos delegando en el registro
existente de adaptadores de dataset. La descripcion de un dataset valida que la
ruta pertenezca a una raiz permitida, infiere o comprueba el adaptador y
devuelve un descriptor compacto sin cargar el dataset completo ni generar
manifiestos. Asimismo, la aplicacion crea un area de staging bajo
`codigo/data/raw/uploads/` para futuras ingestas locales controladas. Esta capa
mantiene `POST /runs` con `dry\_run=true` como preflight canonico de capacidades
antes de ejecutar. La verificacion incluyo tests de catalogo, rechazo de rutas
fuera de raiz, rechazo de adaptadores incompatibles y una nueva compilacion del
frontend.

El tercer avance conecta la interfaz con la ejecucion real en segundo plano ya
disponible en la API. La vista mantiene un boton de planificacion basado en
`dry\_run=true` y habilita la accion de ejecucion solamente cuando el plan
devuelto por el backend es ejecutable. La ejecucion envia `POST /runs` con
`dry\_run=false` y `background=true`, recibe un identificador de job local y
consulta periodicamente `GET /run-jobs/\{job\_id\}`. Cuando el job termina, la
interfaz obtiene el snapshot persistido mediante `GET /runs/\{run\_id\}` y
refresca el registro de ejecuciones. Si el job falla, se muestra el detalle
tecnico devuelto por el backend, preservando la trazabilidad del error sin
confundirlo con un resultado metodologicamente no aprobado.
Como prueba de humo se lanzo una run CWRU en segundo plano, que completo con
snapshot persistido, informe tecnico y artefactos registrados.

El cuarto avance convierte el registro de ejecuciones en una vista operativa.
La interfaz consume los endpoints de lectura ya existentes: `GET /runs` para
listar con filtros, `GET /runs/\{run\_id\}` para cargar el snapshot,
`GET /runs/\{run\_id\}/artifacts` para inspeccionar artefactos,
`GET /runs/\{run\_id\}/report` para previsualizar el informe Markdown y
`GET /runs/compare` para comparar metricas entre varias ejecuciones. De este
modo, la aplicacion no recalcula resultados ni lee ficheros directamente desde
el navegador, sino que reutiliza el registro local persistido y los contratos
`RunIndexEntry`, `RunSnapshot` y `RunComparison`. La vista distingue el fallo de
infraestructura de una ejecucion completada pero no aprobada por metricas,
manteniendo la semantica metodologica del evaluador.

El quinto avance inicia la observabilidad agentica en tiempo real. Se ha
definido el contrato `AgentRuntimeEvent` y un `AgentRuntimeRecorder` que permite
al job en segundo plano acumular eventos de supervisor, agentes, recuperacion de
memoria, ejecutores, estado del job y errores. El grafo LangGraph emite estos
eventos de forma opcional y no bloqueante, de modo que la telemetria no altera
la ejecucion ni sustituye los snapshots persistidos. La API expone los eventos
en `GET /run-jobs/\{job\_id\}` y en `GET
/run-jobs/\{job\_id\}/events`. En el frontend se ha anadido la pestana
`Agentes`, que representa la jerarquia supervisor-agentes, un timeline de
comunicacion y un panel de detalle con `decision\_id`, confianza, `rationale`,
memoria citada y payload JSON observable. Esta vista muestra decisiones y
justificaciones estructuradas, no cadena de pensamiento privada del modelo.

El siguiente incremento completa la visibilidad de memoria persistida. Se ha
anadido una capa API de solo lectura sobre `LocalJsonVectorMemoryStore`, sin
crear otro indice ni modificar la logica de recuperacion RAG de los agentes. La
API expone `GET /memory/collections` para resumir colecciones canonicas,
`GET /memory/records` para listar recuerdos filtrables por agente, dataset, rol,
reutilizacion y texto, y `GET /memory/records/\{memory\_record\_id\}` para
abrir el `ReasoningMemoryRecord` completo. En el frontend, la pestana
`Agentes` muestra para el agente seleccionado la coleccion persistida, numero de
recuerdos, recuerdos reutilizables, busqueda textual y detalle de fuente,
veredicto humano, `run\_id`, `decision\_id` y contenido. La memoria se presenta
como evidencia trazable y no como mecanismo de aprobacion automatica.

El sexto avance hace operativa la revision humana minima desde la interfaz. Se
reutilizan los contratos existentes `HumanReviewSettings` y `HumanApproval`, asi
como las razones `human\_review\_reasons` calculadas por la API durante el
preflight. La UI permite seleccionar el modo `off`, `passive` o `required`,
indicar el revisor, marcar los puntos de revision explicita y, cuando procede,
registrar una aprobacion simple con motivo y fecha. En modo `passive`, las
razones se muestran como advertencia sin bloquear la ejecucion. En modo
`required`, la accion de ejecutar queda bloqueada hasta que exista aprobacion
explicita, manteniendo ademas la validacion del backend como fuente de verdad.
Este incremento no introduce un sistema multiusuario de aprobaciones, sino una
puerta local y trazable coherente con el alcance de Fase 5.

El septimo avance consolida el frontend como herramienta operativa completa. La
interfaz queda organizada en una vista `Pipeline`, que agrupa seleccion de
dataset, preflight, revision humana, ejecucion en segundo plano, seguimiento de
job, registro de runs, detalle, metricas, informe, artefactos y comparacion, y
una vista `Agentes`, que agrupa observabilidad runtime, jerarquia de agentes,
timeline, memoria recuperada y memoria persistida. Para reforzar la trazabilidad
durante la operacion se incorpora una banda de contexto fija con `dataset\_id`,
`run\_id`, modo de ejecucion, politica de dataset, numero de fases, estado del
plan y estado del job. Esta consolidacion no introduce nuevos endpoints ni
runners, sino que integra visualmente los contratos y servicios ya validados en
los hitos anteriores.

Como ampliacion visual de la aplicacion, se ha incorporado una lectura humana
determinista de los eventos agenticos. Junto al `payload` JSON de cada evento,
la interfaz genera una frase que resume el agente responsable, la fase, la
confianza, la siguiente accion propuesta y los campos clave del JSON. Esta
traduccion no pretende revelar cadena de pensamiento privada, sino convertir la
telemetria estructurada en una explicacion operativa comprensible.

Tambien se ha anadido una pestana `Visualizacion` para analizar resultados de
runs persistidas. El backend expone `GET /runs/\{run\_id\}/visualization`, que
lee los artefactos `windows\_features.csv` y `predictions.csv`, une ambos por
`window\_id`, escala las features numericas y calcula una proyeccion PCA en dos
dimensiones. La interfaz muestra barras de metricas y un diagrama de dispersion
con ventanas normales, anomalias detectadas y una frontera visual aproximada. Se
declara explicitamente que esta frontera es una ayuda grafica en la proyeccion
2D, no la frontera exacta del modelo en el espacio original de caracteristicas.

El siguiente ajuste conecta la aplicacion web con los agentes Qwen/Ollama reales.
El contrato `PipelineRunRequest` ya contenia el campo `use\_llm`, pero la API lo
mantenia bloqueado por seguridad durante la primera ejecucion controlada. En
Fase 5 se sustituye ese bloqueo por una comprobacion explicita de disponibilidad:
`GET /llm/status` consulta Ollama local, informa del modelo configurado y verifica
que `qwen3.5:4b` este instalado. Si la interfaz activa `Agentes LLM`, `POST
/runs` con `use\_llm=true` construye un conjunto de agentes con
`OllamaJSONClient` e inyecta ese cliente en supervisor, limpiador,
estructurador, modelador, evaluador y redactor. La ejecucion conserva los
contratos JSON/Pydantic y los fallbacks deterministas ante respuestas invalidas,
por lo que el LLM participa en la decision sin adquirir capacidad de ejecutar
codigo ni modificar directamente los datos.

Finalmente, se ha refactorizado la interfaz de Fase 5 desde una pantalla
tecnica acumulativa hacia un dashboard local de operacion. La aplicacion se
estructura con un shell principal, navegacion lateral, cabecera de estado,
resumen de salud y areas de trabajo separadas para pipeline, agentes y
visualizacion. Dentro de `Pipeline`, la configuracion de la run, el preflight,
la ejecucion y el historial de runs se presentan como bloques diferenciados,
mientras que rutas largas, parametros avanzados y detalles tecnicos quedan en
paneles plegables. Este cambio no altera endpoints ni contratos del backend:
reorganiza visualmente las mismas capacidades para mejorar jerarquia,
legibilidad y mantenibilidad de la aplicacion local.
Como ultimo pulido de interfaz, se evita renderizar rutas locales de ficheros en
la pagina web y el panel de nueva ejecucion deja de comportarse como un bloque
pegajoso durante el desplazamiento vertical.

Con estos elementos, la Fase 5 queda cerrada como aplicacion local avanzada y
defendible. El sistema ya no depende solo de scripts para demostrar el flujo:
permite operar la API desde una interfaz web, ejecutar runs controladas,
seguir jobs, consultar resultados, observar agentes, revisar memoria y analizar
visualizaciones. Las limitaciones que permanecen son deliberadas: no se ha
introducido autenticacion multiusuario, cola persistida, despliegue cloud ni
empaquetado Docker. La siguiente fase se centra precisamente en la
dockerizacion, la reproducibilidad local y la preparacion de una demo final
repetible, manteniendo la misma metodologia de reutilizacion, contratos
estrictos y separacion entre razonamiento generativo y ejecucion determinista.

El primer paso de la Fase 6 no consiste aun en crear imagenes, sino en fijar los
supuestos de entorno. Se documentan los puertos canonicos del sistema local
(`8010` para FastAPI, `5173` para Vite y `11434` para Ollama), las variables de
entorno necesarias para Qwen y embeddings, y los directorios que deberan
montarse como volumenes persistentes (`codigo/data`, `codigo/reports`,
`codigo/models` y `codigo/experiments`). Tambien se decide que Ollama quedara
externo al primer `docker-compose`, de forma que los modelos locales no se
descarguen ni empaqueten dentro de las imagenes iniciales.

El segundo paso prepara la configuracion reproducible sin crear todavia
contenedores. Se añade una plantilla `.env.example` en `codigo/docker/` con las
variables de backend, frontend, LLM, embeddings y volumenes previstos, y se
documenta el uso esperado de la carpeta Docker. Ademas, el proxy de desarrollo
de Vite se hace configurable mediante `VITE\_DEV\_PROXY\_TARGET`, conservando
`http://127.0.0.1:8010` como valor por defecto para el desarrollo local.

El tercer paso define la primera imagen Docker del backend. Se añade un
`.dockerignore` para excluir caches, dependencias frontend, datasets, reports,
modelos, experimentos y recursos academicos del contexto de build, y se crea un
`backend.Dockerfile` basado en `python:3.11-slim`. La imagen instala
`requirements.txt`, copia unicamente el paquete `codigo.app`, crea los
directorios base que despues se montaran como volumenes y arranca la API con
Uvicorn en el puerto `8010`. La verificacion estatica del paquete Python se
ejecuta correctamente. Tras activar Docker Desktop, la imagen
`tfm-backend:fase6-hito3` se construye y se valida con un contenedor publicado
en `8015:8010` para no interferir con la API local ya activa en `8010`. Los
endpoints `GET /health`, `GET /datasets/adapters` y `GET /llm/status` responden
desde el contenedor; este ultimo confirma la comunicacion con Ollama externo a
traves de `host.docker.internal:11434` y disponibilidad del modelo
`qwen3.5:4b`.

El cuarto paso empaqueta el frontend como una imagen estatica reproducible. Se
opta por no ejecutar Vite en modo desarrollo dentro de Docker: la imagen usa
`node:22-alpine` para instalar dependencias con `npm ci` y generar el build
React/Vite, y una segunda etapa `nginx:1.27-alpine` para servir los artefactos
compilados. La variable `VITE\_API\_BASE\_URL` mantiene `/api` como frontera
publica del navegador, mientras que una plantilla Nginx redirige ese prefijo a
`TFM\_BACKEND\_URL`, que en compose apuntara al servicio `backend` y en pruebas
manuales puede apuntar al backend local mediante
`host.docker.internal:8010`. La verificacion confirma que `npm run build` pasa
en local, que la imagen `tfm-frontend:fase6-hito4` se construye correctamente y
que un contenedor publicado en `5174:5173` sirve el HTML del dashboard,
responde a `/healthz` y comunica con la API mediante `/api/health` y
`/api/datasets/adapters`. El healthcheck Docker queda en estado `healthy`.

El quinto paso integra ambas imagenes en un `docker-compose.yml` local. El
servicio `backend` construye la imagen FastAPI, monta `codigo/data`,
`codigo/reports`, `codigo/models` y `codigo/experiments` como bind mounts y
conserva Ollama como dependencia externa mediante
`host.docker.internal:11434`. El servicio `frontend` construye la imagen web,
espera a que el backend este saludable y redirige su proxy `/api` al servicio
interno `backend:8010`. Los puertos publicados en el host quedan
parametrizados, de modo que la validacion se ejecuta en `8016` y `5175` sin
interferir con la API local ya activa en `8010`. La comprobacion de compose
confirma que ambos servicios quedan `healthy`, que el backend responde a
`/health` y `/llm/status`, que el frontend sirve el HTML compilado y que el
proxy Nginx devuelve correctamente `/api/health` y
`/api/datasets/adapters`.

Con este resultado, la Fase 6 queda cerrada operativamente en el Hito 5. La
decision es no automatizar todavia las pruebas de humo ni preparar la demo
final cerrada, porque el siguiente bloque de trabajo volvera a la aplicacion
para pulir funcionalidad, ampliar capacidades, revisar fronteras y mejorar la
experiencia de usuario. Docker queda como base reproducible minima: a partir de
ahora, cada cambio relevante de backend, frontend, dependencias o variables se
desarrollara primero en local y se trasladara despues al stack dockerizado
mediante reconstruccion y validacion manual. Esta decision evita fijar una
secuencia de pruebas sobre una superficie que todavia se espera que evolucione.

\section{Fase 7: evidence pack e informe agentico}

Tras cerrar la base dockerizada minima, la Fase 7 vuelve al nucleo funcional del
TFM: agentes de IA, deteccion autonoma de anomalias y reporte auditable para
analistas humanos. El primer hito se centra en dos necesidades: conservar una
evidencia estructurada de cada ejecucion y hacer que el agente redactor tenga
un papel narrativo real en el informe final, sin romper la separacion entre
razonamiento generativo y ejecucion determinista.

En esta fase se fija ademas un criterio de implementacion para evitar que la
instrumentacion determinista oculte el objetivo investigador. Los agentes
Qwen/LLM conservan el protagonismo como decisores e interpretes del sistema:
el supervisor coordina, el limpiador y estructurador formulan configuraciones,
el modelador plantea hipotesis, el evaluador juzga resultados, el redactor y el
verificador producen y revisan conclusiones. Los ejecutores, herramientas y
visualizaciones deterministas son el soporte que permite que esas decisiones
sean seguras, reproducibles y auditables. Por ello, cada nueva metrica, vista o
herramienta de Fase 7 debe entenderse como una ampliacion del campo de evidencia
de los agentes, no como una sustitucion de la investigacion agentica.

La decision de trabajar con LLM locales relativamente pequenos, como Qwen sobre
Ollama, se conserva como hipotesis metodologica. Su lentitud en una maquina
local no invalida la linea: permite estudiar que ocurre cuando se intenta
acercar un sistema agentico auditable a restricciones industriales de coste,
privacidad, despliegue local y latencia. Si la arquitectura alcanza limites
practicos, esos limites se documentaran como resultado experimental; mientras
tanto, la implementacion seguira intentando llevar la participacion agentica tan
lejos como permitan los contratos estrictos y los guardarrailes de seguridad.

La persistencia local de runs se ha ampliado en \texttt{run\_persistence.py}.
Cada snapshot nuevo puede generar ahora dos artefactos adicionales:

\begin{center}
\begin{minipage}{0.85\textwidth}
\begin{verbatim}
codigo/reports/runs/<run_id>/evidence_pack.json
codigo/reports/runs/<run_id>/evidence_pack.md
\end{verbatim}
\end{minipage}
\end{center}

El primer fichero es el paquete de evidencia auditable. Incluye identificacion
de la run, contexto experimental, configuraciones, metricas, evaluacion,
revision humana si existe, decisiones agenticas normalizadas, errores y
artefactos con estado de existencia y checksum SHA-256 cuando el fichero esta
disponible. El segundo fichero es una vista Markdown resumida para inspeccion
humana rapida. Esta vista no sustituye al informe tecnico final, sino que
ayuda a auditar de donde salen las conclusiones.

Tambien se ha ampliado \texttt{pipeline\_runner.py} para registrar, antes de la
ejecucion, la solicitud exacta y el plan preflight aplicado:

\begin{center}
\begin{minipage}{0.85\textwidth}
\begin{verbatim}
codigo/reports/<dataset>/<run_id>/evidence/pipeline_request.json
codigo/reports/<dataset>/<run_id>/evidence/pipeline_plan.json
\end{verbatim}
\end{minipage}
\end{center}

Estos ficheros son artefactos de tipo \texttt{config} y permiten revisar que se
pidio, que politica de dataset se aplico, que fases eran efectivas y si habia
bloqueos metodologicos antes de transformar datos.

En paralelo, el contrato \texttt{ReportSection} se ha extendido con campos de
contenido humano: cuerpo narrativo, hallazgos principales, recomendaciones y
referencias de evidencia. El agente \texttt{report\_writer} sigue devolviendo
un \texttt{ReportDecision} validado por Pydantic, pero ahora puede redactar las
secciones del informe en castellano tecnico. El JSON sigue siendo un contrato
interno de seguridad y validacion; el documento final para el analista se
materializa como Markdown mediante el ejecutor determinista
\texttt{reporting.py}.

La verificacion del hito se ha realizado con las pruebas de agente redactor,
ejecutor de reporting, persistencia de runs y runner comun. La bateria
ejecutada cubre la redaccion narrativa validada, el renderizado del informe,
la creacion de evidence pack y la inclusion de request/plan como artefactos de
evidencia. Con ello, el sistema queda mejor preparado para una defensa
auditable del TFM: no solo produce metricas, sino que conserva la ruta entre
peticion, plan, decisiones agenticas, artefactos y conclusiones humanas.

La interfaz web se ha ajustado para reflejar esta nueva jerarquia. En el
detalle de una run, el informe ya no aparece como un bloque tecnico al final de
la lista de artefactos, sino como la seccion principal de cierre analitico. El
Markdown servido por la API se transforma en una vista de documento con titulo,
metadatos clave, secciones, parrafos, hallazgos y recomendaciones. La evidencia
tecnica queda debajo, separada visualmente, como soporte auditable del informe.
Ademas, la previsualizacion de la UI filtra rutas locales y bloques de fuentes
tecnicas para mantener la decision de no exponer rutas de fichero en la pagina
web, sin alterar el artefacto Markdown persistido en disco.

Como segundo hito de Fase 7 se ha separado explicitamente el informe final del
agente redactor de una nueva auditoria de ejecucion. Esta auditoria se genera
de forma determinista a partir del \textit{evidence pack} y se persiste como:

\begin{center}
\begin{minipage}{0.85\textwidth}
\begin{verbatim}
codigo/reports/runs/<run_id>/execution_audit.md
\end{verbatim}
\end{minipage}
\end{center}

El objetivo de este documento es que un evaluador humano pueda entender, de un
vistazo y con lenguaje claro, que ocurrio durante toda la run. La auditoria
incluye lectura rapida, solicitud y plan aplicado, cronologia de agentes,
resultado tecnico, metricas, artefactos, checksums abreviados, errores,
bloqueos y consideraciones de revision humana. La API expone este documento
mediante `GET /runs/\{run\_id\}/audit-report`, manteniendo separado el endpoint
del informe final `GET /runs/\{run\_id\}/report`.

En frontend, el detalle de run queda organizado en tres niveles: primero el
informe final de conclusiones generado por `report\_writer`, despues la
auditoria de ejecucion como explicacion operativa del proceso, y finalmente la
evidencia tecnica como lista de artefactos. Esta separacion evita que el
analista confunda el documento narrativo de conclusiones con la traza
determinista de lo que ha ocurrido durante la ejecucion.

El tercer hito introduce una primera capa de verificacion agentica del informe
final. Se ha creado el agente \texttt{report\_verifier}, cuya funcion no es
exigir una redaccion literal ni imponer un estilo concreto, sino detectar
afirmaciones factuales o metodologicas que no esten respaldadas por la
evidencia disponible. El agente recibe el informe Markdown y un catalogo
cerrado de evidencias derivado del estado de la run: dataset, modo de
etiquetas, configuraciones, metricas, evaluacion, limitaciones, artefactos y
politicas metodologicas relevantes. Con esa informacion devuelve una decision
Pydantic \texttt{ReportVerificationDecision} con estado de verificacion,
incidencias, severidad, referencias de evidencia y correcciones requeridas.

La verificacion mantiene una tolerancia explicita sobre orden, enfasis y
formulacion del texto. Lo que se penaliza son afirmaciones no soportadas, como
presentar una ejecucion local como validacion industrial, declarar etiquetas
oficiales en NASA IMS cuando solo existe politica proxy o sintetica, omitir que
una run no fue aprobada o esconder limitaciones persistidas por el evaluador.
Si el LLM no esta disponible, un fallback determinista detecta solo riesgos
evidentes para no convertir esta capa en un script rigido de comparacion
literal.

Tras generarse \texttt{final\_report.md}, el grafo invoca el verificador y
persiste dos artefactos bajo el directorio de evidencias del informe:

\begin{center}
\begin{minipage}{0.85\textwidth}
\begin{verbatim}
<directorio_del_informe>/evidence/report_verification.json
<directorio_del_informe>/evidence/report_verification.md
\end{verbatim}
\end{minipage}
\end{center}

El primer fichero conserva la decision estructurada y el segundo ofrece una
lectura humana de incidencias y correcciones. La auditoria de ejecucion incorpora
ademas un bloque especifico de verificacion del informe.

El cuarto hito implementa ya ese debate controlado entre
\texttt{report\_writer} y \texttt{report\_verifier}. Se ha anadido el contrato
\texttt{ReportRevisionDecision} para que el redactor responda a las incidencias
del verificador sin conversacion libre, indicando que problemas acepta o rechaza,
que cambios aplica y que evidencias conserva. En paralelo, los contratos
\texttt{ReportDebateTurn} y \texttt{ReportDebateRecord} registran una vista
ordenada del intercambio: borrador inicial, verificacion, revision, nueva
verificacion y cierre del debate.

La version implementada mantiene una sola ronda de revision. Si el informe
inicial es aceptado, el debate termina como
\texttt{approved\_without\_revision}. Si el verificador solicita cambios, el
redactor genera una version revisada y el verificador la evalua de nuevo. Si
tras esa ronda quedan incidencias, el resultado pasa a
\texttt{needs\_human\_review} o \texttt{blocked}, evitando aprobar
silenciosamente un informe con afirmaciones no soportadas.

El coordinador del debate se ha aislado en \texttt{report\_debate.py}. Este
servicio no toma decisiones agenticas nuevas; solo compone los turnos y
persiste los artefactos humanos y estructurados:

\begin{center}
\begin{minipage}{0.85\textwidth}
\begin{verbatim}
<directorio_del_informe>/evidence/report_debate.json
<directorio_del_informe>/evidence/report_debate.md
<directorio_del_informe>/evidence/final_report_initial.md
<directorio_del_informe>/evidence/final_report_revision_001.md
\end{verbatim}
\end{minipage}
\end{center}

La API expone el debate mediante
\texttt{GET /runs/\{run\_id\}/report-debate}. La interfaz web carga ese
Markdown y lo muestra como seccion propia despues del informe final y la
auditoria de ejecucion. Tambien se ha anadido \texttt{report\_verifier} a la
vista de agentes y se han mejorado las traducciones humanas de eventos para que
campos como estado de verificacion, ronda, resumen, correcciones y cambios sean
legibles sin abrir el JSON completo.

Sobre esa base se ha incorporado una conversacion agentica en la pestana de
agentes. Esta vista toma los eventos runtime de supervisor y agentes, descarta
ruido de job y ejecutores, y los presenta como mensajes ordenados con nombre,
rol, accion resumida, fase y pequenos indicadores de confianza, memoria o
veredicto. Cada mensaje permite seleccionar el agente correspondiente para ver
el detalle tecnico cuando sea necesario. Asi, el evaluador humano puede seguir
de un vistazo el hilo real de trabajo: supervisor, limpiador, estructurador,
modelador, evaluador, redactor y verificador.

La validacion posterior con una run completa ha permitido refinar la tolerancia
del verificador. En particular, se ha evitado que frases de acotacion como
``no equivale a validacion industrial final'' se interpreten como afirmaciones
industriales no soportadas. Tambien se ha saneado la caida a fallback cuando el
LLM devuelve un JSON con nombres de campo no canonicos: el sistema normaliza
alias frecuentes antes de validar con Pydantic y, si aun asi debe usar el
verificador determinista, no expone errores de validacion crudos en la interfaz.

El siguiente avance inicia la expansion controlada de herramientas para los
agentes. Se han definido contratos Pydantic de especificacion, solicitud y
observacion de herramienta, que permiten declarar herramientas elegibles por los
LLM sin que estas sustituyan su decision. La
primera herramienta es \texttt{evidence\_lookup}, de solo lectura, orientada a
consultar evidencia de una ejecucion: contexto del proyecto, configuraciones,
metricas, evaluacion, artefactos, errores y politica del dataset. Su salida es
una observacion estructurada con referencias citables como
\texttt{metric:recall}, \texttt{evaluation:approved} o
\texttt{artifact:evaluation\_metrics}. La herramienta no modifica datos ni
artefactos; solo amplia el espacio de observacion disponible para futuras
decisiones agenticas. Ademas, el verificador del informe reutiliza el mismo
catalogo cerrado de evidencias, reduciendo duplicacion y preparando una frontera
comun para herramientas posteriores.

La segunda herramienta del catalogo es \texttt{threshold\_analysis}. Esta
herramienta lee el artefacto de predicciones registrado en el estado y calcula
un diagnostico de sensibilidad: metricas por cuantiles de score, matriz de
confusion, resumen de distribucion de scores y ventanas cercanas al umbral
actual. Su salida incluye un guardarrail explicito: el analisis no selecciona
un umbral ni sustituye la comparacion entre modelos. Para reforzar esta idea,
la decision del modelador se ha ampliado con una estrategia declarada
(\texttt{ModelingDecisionStrategy}), donde el agente debe explicitar si su
hipotesis es seleccion de familia de modelo, calibracion de umbral, ajuste entre
features y modelo, riesgo de particion, conservacion de baseline o falta de
evidencia. Cuando la estrategia declarada es calibracion de umbral, el contrato
exige mantener al menos una alternativa de otra familia de modelo en
\texttt{comparison\_candidates}. Asi el umbral se trata como una evidencia de
diagnostico, no como la unica via de mejora del agente.

Como tercera ampliacion del espacio de modelado se ha incorporado One-Class
SVM, expuesto en la aplicacion como \texttt{one\_class\_svm}. Este modelo
mantiene la frontera metodologica no supervisada del pipeline: se entrena solo
con ventanas normales del split \texttt{train} y produce un
\texttt{anomaly\_score} comparable con el resto de detectores, donde valores
mas altos indican mayor anomalia. La implementacion
usa \texttt{StandardScaler} y \texttt{sklearn.svm.OneClassSVM}, valida
hiperparametros como \texttt{kernel}, \texttt{nu}, \texttt{gamma},
\texttt{tol}, \texttt{shrinking} y \texttt{max\_iter}, y persiste el modelo,
las predicciones y el resumen de modelado igual que las familias anteriores.
El agente modelador puede ahora comparar \texttt{isolation\_forest},
\texttt{pca\_reconstruction\_error} y \texttt{one\_class\_svm}. En cambio,
XGBoost se ha dejado fuera de esta etapa porque representa un baseline
supervisado que solo debe introducirse cuando exista un dataset y una politica
de etiquetas adecuados.

Como ajuste intermedio antes de continuar ampliando el modelador, se ha
estabilizado la ejecucion NASA IMS desde la aplicacion. El formulario web usa
ahora por defecto la muestra preextraida local, el modo \texttt{full} y la
politica \texttt{nasa\_ims\_temporal\_v1}, de modo que el preflight permite
modelado, evaluacion y reporte sin presentar las etiquetas proxy como
oficiales. Ademas, el endpoint de visualizacion puede construir una proyeccion
PCA diagnostica cuando existen features persistidas pero aun no hay
predicciones. En ese caso los puntos se muestran sin puntuacion de anomalia ni
frontera, con una advertencia explicita para distinguir una run diagnostica de
una run evaluada. La validacion local de NASA IMS confirma que completa el
flujo, genera informe, metricas, predicciones y visualizacion; las metricas no
se aprueban por \texttt{FPR}=1.0, lo que se conserva como limitacion
metodologica en lugar de ocultarlo como fallo tecnico.

El siguiente paso de Fase 7 introduce perfiles explicitos de supervision para
separar datasets binarios con etiquetas directas de secuencias
run-to-failure. Las referencias revisadas sobre NASA IMS, la libreria de
metricas pronosticas de NASA, XJTU-SY y PRONOSTIA/IEEE PHM 2012 justifican que
los ensayos de degradacion se modelen como trayectorias temporales hasta fallo,
no como clasificacion binaria por ventana salvo que exista una politica proxy
declarada \cite{nasa_ims_datagov,nasa_prognostics_metrics_library,xjtu_sy_bearing_dataset,ieee_phm_2012_pronostia_challenge}.
Por ello se han anadido \texttt{supervision\_profile},
\texttt{label\_source} y \texttt{label\_granularity} a
\texttt{DatasetDescriptor} y \texttt{ProjectContext}. La declaracion inicial
queda fijada asi:

\begin{center}
\begin{minipage}{0.85\textwidth}
\begin{verbatim}
CWRU:
  supervision_profile = binary_fault_classification
  label_source = official
  label_granularity = file

NASA IMS:
  supervision_profile = run_to_failure_degradation
  label_source = none | temporal_proxy | synthetic
  label_granularity = event | proxy_temporal | file
\end{verbatim}
\end{minipage}
\end{center}

En NASA IMS, el valor \texttt{temporal\_proxy} solo aparece cuando se usa la
politica \texttt{nasa\_ims\_temporal\_v1}. La aplicacion web muestra estos
campos en el preflight para que el usuario vea antes de lanzar una run que tipo
de evidencia y supervision se esta usando.

El segundo paso del mismo hito extiende el manifiesto comun sin crear otro
formato paralelo. La lectura y escritura CSV de \texttt{CommonManifestRecord}
se ha centralizado en \texttt{common\_manifest.py}, eliminando duplicacion entre
adaptadores, politica temporal NASA IMS y benchmarks sinteticos. El manifiesto
NASA IMS base conserva ahora los timestamps por snapshot y anade en
\texttt{metadata\_json} los metadatos run-to-failure generales:

\begin{center}
\begin{minipage}{0.85\textwidth}
\begin{verbatim}
failure_event_time
failure_mode
end_of_life_policy
official_window_labels = false
label_source = none
label_granularity = event
\end{verbatim}
\end{minipage}
\end{center}

Cuando se aplica \texttt{nasa\_ims\_temporal\_v1}, esos metadatos se preservan
y solo se declara una nueva capa de supervision proxy:

\begin{center}
\begin{minipage}{0.85\textwidth}
\begin{verbatim}
label_source = temporal_proxy
label_granularity = proxy_temporal
label_policy_id = nasa_ims_temporal_v1
\end{verbatim}
\end{minipage}
\end{center}

Asi, el pipeline dispone de informacion temporal/fallo suficiente para las
siguientes fases, pero sigue sin presentar etiquetas por ventana como oficiales.

El tercer paso propaga esa informacion hasta el nivel de ventana. En lugar de
crear un estructurador especifico para NASA IMS, se ha extendido la cadena
existente. El ejecutor \texttt{cleaning.py} conserva en cada fichero limpio:

\begin{center}
\begin{minipage}{0.85\textwidth}
\begin{verbatim}
source_path
condition_id
asset_id
run_id
timestamp_start
timestamp_end
\end{verbatim}
\end{minipage}
\end{center}

Despues, \texttt{structuring.py} transforma esos campos en columnas por ventana
dentro de \texttt{windows\_features.csv}. Las nuevas columnas son:

\begin{center}
\begin{minipage}{0.85\textwidth}
\begin{verbatim}
run_id
asset_id
condition_id
timestamp_start
timestamp_end
time_since_start_seconds
time_to_failure_seconds
relative_life
\end{verbatim}
\end{minipage}
\end{center}

La vida relativa solo se calcula cuando el run tiene timestamps y evento de
fallo declarado. Para evitar fugas, \texttt{modeling.py} y
\texttt{run\_visualization.py} tratan estas columnas como metadatos y no como
features numericas de entrenamiento o proyeccion. El ejecutor de modelado las
preserva en \texttt{predictions.csv}, preparando el siguiente paso de evaluacion
temporal de degradacion.

El cuarto paso incorpora esa evaluacion temporal sin crear un evaluador paralelo.
Se ha extendido \texttt{evaluation.py}, que sigue siendo el propietario canonico
de las metricas de prediccion, para que detecte de forma generica si
\texttt{predictions.csv} contiene \texttt{relative\_life},
\texttt{anomaly\_score} y \texttt{predicted\_anomaly}. Cuando esos campos
estan disponibles, el artefacto \texttt{metrics.json} declara dos familias:
\texttt{binary\_classification} y \texttt{run\_to\_failure\_degradation}. La
primera mantiene las metricas previas de precision, recall, F1, ROC-AUC,
PR-AUC, FPR y matriz de confusion; la segunda calcula metricas por trayectoria,
incluyendo primera alerta, tiempo hasta deteccion, \texttt{lead\_time} hasta
fallo, falsas alarmas en tramo nominal, persistencia de alertas, correlacion
Spearman del score con la vida relativa, pendiente, separacion inicial-final,
monotonicidad y fallos no detectados.

Esta separacion evita presentar una politica proxy temporal como si fuera una
etiqueta oficial por ventana. Si el origen de etiqueta no viaja dentro del CSV
de predicciones, el evaluador deja una advertencia en el contexto binario y el
resumen Markdown muestra una seccion diferenciada de degradacion. A su vez, el
grafo copia al estado solo un resumen plano de esta familia en
\texttt{MetricsReport.extra}, manteniendo compatible el contrato existente y
permitiendo que los agentes posteriores razonen sobre \texttt{lead\_time},
falsas alarmas nominales y tendencia sin mezclar estructuras anidadas en el
estado global.

El quinto paso traslada esta informacion a la aplicacion visual sin crear un
endpoint paralelo. El contrato \texttt{RunVisualizationData} se ha extendido con
un bloque opcional \texttt{temporal\_series}, formado por
\texttt{TemporalSeriesData}, \texttt{TemporalRunSeries} y
\texttt{TemporalSeriesPoint}. El servicio \texttt{run\_visualization.py}
construye dicho bloque directamente desde \texttt{predictions.csv}; selecciona
como eje temporal, por prioridad, \texttt{relative\_life},
\texttt{time\_since\_start\_seconds} o \texttt{window\_index}. Para cada
trayectoria conserva el score de anomalia, el umbral, la primera alerta, el
tiempo restante hasta fallo cuando existe, un marcador de fallo estimado y una
muestra compacta de puntos para no saturar la API.

La interfaz web mantiene la misma pestana de visualizacion, pero anade una vista
principal de degradacion antes de la proyeccion PCA. Esta vista dibuja la curva
del \texttt{anomaly\_score}, la linea de umbral, el primer aviso y el fallo
estimado si los metadatos lo permiten. Si las predicciones no contienen
metadatos temporales suficientes, el backend devuelve
\texttt{temporal\_series.available = false} con advertencias legibles y la PCA
sigue funcionando como vista secundaria. De esta forma, NASA IMS y futuros
datasets run-to-failure pueden inspeccionarse como trayectorias temporales sin
perder compatibilidad con las runs binarias de CWRU.

El sexto paso hace que los agentes posteriores sean conscientes del perfil de
supervision. En \texttt{modeler.py}, el contexto entregado al LLM y al fallback
incluye el perfil de supervision, la fuente de etiquetas y su granularidad.
Para el perfil de degradacion temporal, el
fallback selecciona \texttt{pca\_reconstruction\_error} como indicador temporal
interpretable y declara que la hipotesis se evaluara por tendencia, primera
alerta y falsas alarmas nominales, no por F1 como objetivo principal. Ademas,
se rechaza una decision cuyo \texttt{strategy\_type} principal sea
\texttt{threshold\_calibration} en este perfil, manteniendo el umbral como
elemento auxiliar para disparar alertas.

En \texttt{evaluator.py}, la politica binaria previa se conserva para CWRU y
perfiles equivalentes: recall y tasa de falsos positivos siguen siendo los
umbrales deterministas. En cambio, cuando el contexto declara
\texttt{run\_to\_failure\_degradation}, la aprobacion se calcula con metricas
temporales: deteccion antes del fallo, falsas alarmas en tramo nominal y
tendencia Spearman del score. En ese caso, \texttt{min\_recall\_required} y
\texttt{max\_false\_positive\_rate} quedan a \texttt{null} en la decision del
agente para no presentar el criterio binario como vinculante. La ausencia de
etiquetas oficiales por ventana no invalida por si sola la run si existen
metricas temporales, aunque se conserva como limitacion metodologica.

Por ultimo, \texttt{report\_writer.py} y \texttt{report\_verifier.py} incorporan
la misma frontera. El redactor presenta lead time, falsas alarmas nominales y
tendencia como metricas principales en informes run-to-failure, dejando F1 solo
como apoyo si procede de una politica proxy. El verificador bloquea cualquier
afirmacion que atribuya etiquetas oficiales o \textit{ground truth} oficial
cuando \texttt{label\_source} no es \texttt{official}. La herramienta
\texttt{evidence\_lookup} expone referencias cerradas para
\texttt{supervision\_profile}, \texttt{label\_source},
\texttt{label\_granularity} y \texttt{metric\_extra:*}, de forma que los
agentes puedan citar evidencia temporal sin inventar campos.

La comprobacion posterior se realizo con la run
\texttt{fase7-paso7-nasa-common-long-v2}, generada sobre una secuencia
NASA-like local de 24 snapshots mediante el runner comun y la politica
\texttt{nasa\_ims\_temporal\_v1}. La ejecucion produjo 168 ventanas con
\texttt{label\_source=temporal\_proxy} y
\texttt{label\_granularity=proxy\_temporal} preservados hasta
\texttt{predictions.csv}; \texttt{metrics.json} declaro la familia
\texttt{run\_to\_failure\_degradation}, el informe fue aprobado por el
verificador y la visualizacion temporal quedo disponible. Durante esta
validacion se ajusto el verificador para no bloquear frases negadas como
``las etiquetas no son oficiales'', manteniendo el bloqueo para afirmaciones
positivas de oficialidad sin evidencia.

El siguiente refinamiento convierte esa evaluacion temporal en una herramienta
comparativa dentro de la aplicacion. La ruta existente \texttt{GET
/runs/compare}, implementada sobre \texttt{run\_registry.py}, se ha extendido
para que cada fila de comparacion incluya el perfil de supervision, la fuente y
granularidad de etiquetas, el modelo usado y las familias metricas disponibles.
Cuando una run contiene metricas \texttt{run\_to\_failure\_degradation}, la
respuesta anade un bloque especifico con comparaciones de deteccion antes de
fallo, \texttt{lead\_time} medio, falsa alarma nominal media, tendencia Spearman
del score, fallos perdidos y separacion inicial-final si esta disponible. La
interfaz web muestra este bloque antes de las metricas binarias, de forma que el
analista compare modelos temporales por comportamiento de degradacion y no por
F1 como criterio principal. Esta decision mantiene la compatibilidad con CWRU y
prepara el panel de investigacion para comparar familias como
\texttt{pca\_reconstruction\_error}, \texttt{isolation\_forest} y
\texttt{one\_class\_svm} sobre el mismo protocolo run-to-failure.

A partir de esa comparacion se ha incorporado una capa de monitorizacion de
estado de salud. La serie temporal ya no se limita a mostrar el score bruto:
\texttt{run\_visualization.py} deriva para cada ventana un
\texttt{risk\_index}, un \texttt{health\_index}, un
\texttt{health\_state} y una razon textual del estado. Si existe umbral, el
riesgo se calcula a partir de la relacion entre \texttt{anomaly\_score} y
\texttt{threshold}; si no existe, se usa una normalizacion interna del score
como aproximacion diagnostica. Los estados resultantes son
\texttt{nominal}, \texttt{watch}, \texttt{warning} y \texttt{critical}. La
trayectoria completa conserva tambien el estado actual, el riesgo y salud
actuales, el numero de puntos en alerta y el tiempo restante hasta fallo solo
cuando este aparece como metadato de un replay historico. De esta forma, la
aplicacion se aproxima a una monitorizacion industrial de activos sin afirmar
una prediccion RUL real cuando el modelo aun no la produce.

El siguiente ajuste traslada esa informacion a una lectura mas humana dentro de
la pestana \texttt{Visualizacion}. El contrato
\texttt{RunVisualizationData} declara ahora el perfil de supervision, fuente y
granularidad de etiquetas, modelo usado, familias metricas, metricas primarias
y metricas auxiliares. Para \texttt{run\_to\_failure\_degradation}, las
metricas principales pasan a ser deteccion antes de fallo, \texttt{lead\_time},
falsas alarmas nominales, tendencia del score, fallos perdidos y separacion
inicio-final. Precision, recall, F1, FPR, ROC-AUC y PR-AUC se conservan como
metricas binarias auxiliares cuando proceden de una politica proxy.

En la interfaz, la misma pestana se vuelve sensible al perfil. Si la run es
run-to-failure, se muestra un panel de control del motor con estado actual,
salud, riesgo, primer aviso, \texttt{lead\_time}, alertas, puntos criticos, una
tira de ventanas coloreada por estado y un flujo compacto
\texttt{ventanas -> detector -> estado -> agente}. La curva temporal existente
se mantiene como lectura tecnica, pero incorpora bandas de estado para facilitar
la interpretacion. La proyeccion PCA se conserva como diagnostico 2D de
features; la interfaz aclara que la elipse dibujada es una aproximacion visual
y no la frontera real del detector ni la metrica principal del perfil temporal.

Tras revisar la interpretacion visual, se ha separado explicitamente un pico
puntual de una alerta sostenida. Cada ventana se evalua localmente, por lo que
un score critico aislado puede ir seguido de una ventana nominal sin implicar
que el motor haya fallado y se haya recuperado. Para evitar esa lectura, la
visualizacion distingue entre \texttt{primer pico} y
\texttt{aviso sostenido}, definido como una racha minima de ventanas
consecutivas en \texttt{warning} o \texttt{critical}. Tambien muestra picos
aislados, episodios de alerta y racha maxima. El fallo mostrado sigue siendo un
marcador historico del replay cuando existe \texttt{time\_to\_failure\_seconds};
no se presenta como una prediccion RUL real del modelo.

\section{Fase 8: adaptacion agentica del perfil run-to-failure}

Con la base temporal y visual del perfil
\texttt{run\_to\_failure\_degradation} preparada, la siguiente fase desplaza el
centro de gravedad hacia los agentes Qwen/LLM. El objetivo ya no es solo que el
pipeline calcule metricas temporales y las muestre en la interfaz, sino que los
agentes gobiernen la investigacion dentro de contratos estrictos: observar
evidencia temporal, formular hipotesis, elegir herramientas, seleccionar modelo
y politica de alerta, debatir resultados, recomendar acciones y generar memoria
reutilizable.

La metodologia mantiene la separacion de seguridad: los LLM no ejecutan codigo
arbitrario ni transforman datos directamente. Sus decisiones se validan mediante
contratos Pydantic y los ejecutores deterministas aplican las acciones
materiales. La diferencia respecto a la fase anterior es de protagonismo:
\texttt{run\_to\_failure\_degradation} pasa a ser el caso principal para
estudiar si agentes locales pequenos pueden conducir una monitorizacion
industrial compleja con evidencia, debate y auditoria. Histeresis avanzada, RUL
experimental y autoencoders se trataran despues de cerrar esta base agentica,
para que esas ampliaciones tambien dependan de decisiones de agentes y no solo
de reglas fijas.

El primer hito de esta fase introduce un paquete de evidencia temporal para
agentes. La herramienta \texttt{evidence\_lookup} incorpora una seccion
\texttt{temporal} que resume, sin cargar CSV completos en el estado, el perfil
\texttt{run\_to\_failure\_degradation}: estado actual de la trayectoria, primer
pico, primer aviso sostenido, episodios de alerta, picos aislados, racha maxima,
referencia de fallo historico, metricas de degradacion y advertencias sobre
etiquetas proxy y RUL no estimado. Esta evidencia se deriva de la misma serie
temporal que alimenta el panel visual, evitando una interpretacion paralela
para agentes.

Ademas, se refuerza el papel del agente \texttt{cleaner}. Su prompt LLM recibe
contexto temporal especifico para razonar sobre canal, frecuencia, valores no
finitos y normalizacion como decisiones que condicionan la continuidad temporal
y la estabilidad del score posterior. El agente no decide fallos ni estima RUL;
mantiene su frontera de calidad de senal, pero con protagonismo dentro del
perfil temporal que gobiernan los agentes Qwen/LLM.

El segundo hito convierte esa evidencia agregada en herramientas agenticas
especificas. Se incorporan \texttt{temporal\_health\_lookup}, que devuelve
estado de salud, primer pico, aviso sostenido, episodios, picos aislados, racha
maxima y referencia de fallo historico, y
\texttt{degradation\_metrics\_lookup}, que devuelve metricas temporales
primarias y contexto de etiquetas. Ambas herramientas son de solo lectura y
generan referencias citables; no aprueban ejecuciones, no eligen modelos y no
estiman RUL. Con ello, los agentes ganan capacidad de eleccion informada sin
romper la arquitectura: \texttt{cleaner}, \texttt{structurer},
\texttt{modeler} y \texttt{evaluator} siguen tomando decisiones en contratos
propios, mientras que los ejecutores deterministas siguen aplicando las acciones
materiales.

El tercer hito especializa al agente \texttt{modeler} como estratega
run-to-failure. En lugar de introducir un contrato paralelo, se extiende
\texttt{ModelingDecisionStrategy} con tres campos compatibles:
\texttt{tool\_names}, \texttt{optimization\_targets} y
\texttt{alert\_policy}. Para el perfil
\texttt{run\_to\_failure\_degradation}, la decision del modelador debe declarar
el uso de \texttt{temporal\_health\_lookup} y
\texttt{degradation\_metrics\_lookup}, citar referencias temporales o metricas
de degradacion, optimizar deteccion antes de fallo, lead time, falsas alarmas
nominales y tendencia del score, y describir una politica que separe pico
aislado, aviso sostenido y umbral auxiliar. F1 queda restringida a metrica
auxiliar. El fallback seguro tambien se adapta a este marco: conserva
\texttt{pca\_reconstruction\_error} como score interpretable, pero deja
herramientas, objetivos, evidencia y alternativas comparables trazadas.

El cuarto hito extiende al agente \texttt{evaluator} como auditor operacional
del perfil temporal. \texttt{EvaluationDecision} incorpora campos compatibles
para registrar herramientas, referencias de evidencia, una valoracion
operacional, puntos de debate temporal y comprobaciones de guardarrail. En
\texttt{run\_to\_failure\_degradation}, el evaluador debe citar
\texttt{temporal\_health\_lookup} y
\texttt{degradation\_metrics\_lookup}, debatir pico aislado frente a aviso
sostenido, declarar que RUL no esta estimado, mantener F1 como metrica auxiliar
y advertir que las etiquetas proxy no son oficiales por ventana. La base del
debate temporal queda integrada en la decision del evaluador y se conserva en
la memoria de decisiones para futuras runs, sin crear todavia un contrato
separado de debate.

El quinto hito traslada esa decision agentica al panel principal de
visualizacion. El contrato \texttt{RunVisualizationData} incorpora
\texttt{AgentOperationalRecommendation}, derivado de los mensajes JSON
persistidos de \texttt{evaluator} y contextualizado con la ultima estrategia de
\texttt{modeler}. La interfaz muestra la recomendacion operacional, confianza,
siguiente accion, evidencia citada, herramientas usadas, guardarrails, cautelas
y puntos de debate. Si una ejecucion esta aprobada pero mantiene limitaciones
metodologicas, la recomendacion se presenta como cautela y no como aprobacion
limpia. De este modo, el panel no sustituye al agente por reglas de interfaz:
hace visible la interpretacion Qwen/LLM y conserva su trazabilidad dentro de la
monitorizacion run-to-failure.

El sexto hito adapta el post-mortem y la memoria agentica al perfil temporal sin
crear un sistema paralelo. En lugar de definir un contrato independiente
\texttt{RunToFailurePostMortem}, se extienden los episodios canonicos
\texttt{DecisionEpisode} y los candidatos \texttt{MemoryCandidate}. El servicio
\texttt{decision\_memory.py} genera ahora episodios del \texttt{modeler} con la
familia de modelo elegida, hipotesis, herramientas temporales, referencias de
evidencia, objetivos de optimizacion y politica de alerta. Para
\texttt{run\_to\_failure\_degradation}, estos episodios incorporan lecciones
sobre metricas temporales, F1 como metrica auxiliar y necesidad de declarar la
politica de aviso.

La memoria del \texttt{evaluator} tambien se especializa para este perfil. Las
metricas de degradacion almacenadas en \texttt{MetricsReport.extra}, como
\texttt{degradation\_mean\_lead\_time\_to\_failure} o
\texttt{degradation\_mean\_false\_alarm\_rate\_nominal}, se trasladan a
\texttt{after\_metrics} del episodio y al contenido indexable del candidato de
memoria. Ademas, una aprobacion temporal con limitaciones se marca como
\texttt{partially\_supported}, de forma que la memoria futura la trate como caso
de frontera y no como ejemplo positivo simple. Los tags del candidato incluyen
tradeoffs y guardarrails como \texttt{rul\_not\_estimated},
\texttt{sustained\_alert\_required} o \texttt{isolated\_spike\_not\_failure},
facilitando su recuperacion vectorial por consultas futuras.

Finalmente, el grafo escribe artefactos de memoria del \texttt{modeler} cuando
\texttt{PipelineMemoryConfig.generate\_decision\_memory} esta activo:
\texttt{modeler\_decision\_episode}, su informe legible,
\texttt{modeler\_memory\_candidate} y su informe. Las ejecuciones sin memoria
activa no cambian comportamiento. Con ello, el perfil temporal empieza a cerrar
el ciclo de aprendizaje: las decisiones Qwen/LLM dejan una traza estructurada e
indexable sobre estrategias de degradacion, no solo un resultado numerico final.

A partir de este punto se define una hoja de ruta especifica para elevar el
sistema de memoria. El diagnostico distingue entre la memoria RAG local ya
implementada y una base vectorial industrial completa: actualmente
\texttt{LocalJsonVectorMemoryStore} persiste colecciones por agente en JSON,
calcula similitud coseno y puede usar \texttt{qwen3-embedding:0.6b} via Ollama,
con \texttt{LocalHashEmbeddingModel} como fallback reproducible. Esta solucion
es suficiente como baseline auditable del TFM, pero no incorpora todavia
Qdrant, Weaviate, Chroma, Milvus, \texttt{pgvector}, busqueda hibrida, reranking
ni evaluacion sistematica del retrieval.

La hoja de ruta avanzada propone primero hacer visible la memoria en frontend:
estado del recuerdo, ciclo candidato--indexado--recuperado--usado--auditado,
consultas realizadas, similitudes, filtros, modelo de embeddings y citas usadas
por cada decision. Solo despues se plantea mejorar el backend con Qdrant,
reranking Qwen, busqueda hibrida y consolidacion/reflexion de recuerdos. Esta
secuencia conserva el principio agentico del trabajo: la memoria informa a los
agentes Qwen y aumenta su capacidad deliberativa, pero no sustituye su decision
ni convierte la ejecucion en un conjunto de reglas deterministas.

El primer hito de esta linea transforma la vista de memoria persistida de la
pestana de agentes en un cockpit operativo. La interfaz muestra contadores por
coleccion, recuerdos reutilizables, datasets, excluidos, distribucion por rol y
origen, asi como un ciclo visual de candidatos, indexados, recuperados en
runtime, usados por agentes y auditorias. Los identificadores de memoria citados
por eventos agenticos pasan a ser navegables y el detalle del recuerdo incorpora
veredicto, origen, resultado, modelo de embedding, dimension,
\texttt{vector\_id}, tags,
metricas, contenido indexable y ruta de origen. Este hito no cambia la API ni
el store JSON local; su funcion es hacer observable la memoria existente antes
de introducir Qdrant, reranking o busqueda hibrida.

El segundo hito completa la observabilidad de retrieval. El grafo persiste
ahora, para cada recuperacion de memoria dentro del flujo principal, un
\texttt{memory\_query.json} separado del
\texttt{retrieved\_memory\_context.json}. La query conserva \texttt{query\_id},
agente objetivo, texto de consulta, dataset, \texttt{run\_id},
\texttt{decision\_id}, contexto de decision, roles permitidos,
\texttt{top\_k} y \texttt{min\_similarity}. El contexto recuperado conserva
items, ranking, similitud, uso previsto, backend y modelo de embeddings.

La telemetria runtime distingue ahora fases del retrieval mediante
\texttt{retrieval\_event}: consulta no disponible, consulta solicitada,
contexto recuperado, memoria usada y memoria ignorada por el agente. En la
interfaz, el cockpit muestra backend, embedding, parametros de consulta,
extracto de query, items recuperados con score, rol, origen y dataset, ademas
de recuerdos citados o ignorados. Esta trazabilidad permite reconstruir una
decision con memoria desde la UI y prepara el siguiente paso: que el
\texttt{modeler} consulte memoria antes de su primera decision de modelo.

El tercer hito lleva esa recuperacion a la decision inicial del modelador y
anade gobierno operativo de recuerdos. \texttt{ModelingDecision} declara ahora
\texttt{memory\_context\_id}, \texttt{used\_memory\_context},
\texttt{memory\_record\_ids}, \texttt{memory\_usage\_summary} y
\texttt{memory\_record\_uses}. La consulta
\texttt{build\_modeler\_memory\_query} incluye dataset, objetivo, perfil de
supervision, fuente de etiquetas, resumen de features y preguntas sobre familia
de modelo, politica temporal, falsos avisos, lead time y uso auxiliar de F1. El
prompt Qwen recibe los recuerdos recuperados y una guia derivada de warnings o
casos frontera, pero la validacion impide citar recuerdos no recuperados y
exige mitigacion explicita si se usa una advertencia.

La memoria se mantiene como capacidad transversal, no como herramienta
exclusiva del modelador. El backend conserva colecciones por agente
(\texttt{cleaner\_memory}, \texttt{structurer\_memory},
\texttt{modeler\_memory}, \texttt{evaluator\_memory},
\texttt{report\_writer\_memory} y memoria metodologica compartida), y el mismo
contrato de recuperacion/cita puede ampliarse a cada nodo del grafo. Para
facilitar benchmarks y pruebas exploratorias, la API y el cockpit permiten
excluir un recuerdo del RAG sin perder trazabilidad, restaurarlo o borrarlo del
indice local. Esta curacion manual prepara comparaciones con memoria completa,
memoria filtrada o memoria desactivada, manteniendo el protagonismo de Qwen:
la memoria informa su decision, pero no la sustituye por una politica
determinista.

Para comprobar si la memoria produce algun efecto observable se ha implementado
un benchmark offline sobre snapshots persistidos. El servicio
\texttt{memory\_effect\_benchmark.py} y el script
\texttt{benchmark\_memory\_effect.py} cargan una o varias runs, leen los
artefactos \texttt{\{agent\}\_retrieved\_memory\_context}, contrastan recuerdos
recuperados frente a recuerdos citados y clasifican cada ejecucion como memoria
no observada, consulta sin recuerdos, retrieval ignorado, memoria usada o uso
invalido. Si se indica una run baseline, el informe anade deltas de
configuracion y metricas sin atribuir causalidad automaticamente.

Como primera evidencia real se ha comparado
\texttt{cwru-memory-transversal-fase4-001} con
\texttt{cwru-memory-transversal-fase4-002-llm}. El informe generado en
\texttt{codigo/reports/memory\_benchmarks/cwru-memory-transversal-fase4-m4-pre}
concluye que la memoria fue recuperada y citada por \texttt{structurer} y
\texttt{evaluator}, sin uso invalido. Las metricas binarias permanecen iguales
respecto al baseline. Por tanto, en este par concreto la memoria si aporta
deliberacion y trazabilidad agentica, pero no demuestra todavia una mejora
numerica de rendimiento.

El siguiente refinamiento incorpora un quality gate determinista sin consolidar
recuerdos. El servicio \texttt{memory\_quality\_gate.py} clasifica cada recuerdo
recuperado como \texttt{pass}, \texttt{caution} o
\texttt{exclude\_candidate}. La decision se basa en similitud, coherencia de
dataset y perfil, rol del recuerdo, veredicto humano, tags de exclusion manual
y procedencia del recuerdo. Las cautelas no bloquean automaticamente al agente:
sirven para dejar evidencia de que un caso frontera, warning o recuerdo parcial
requiere mitigacion explicita.

El benchmark se ha ampliado ademas con variantes controladas como
\texttt{memory\_off}, \texttt{memory\_full}, \texttt{memory\_filtered},
\texttt{memory\_conflict\_excluded} y \texttt{retrieval\_only}. Al regenerar el
smoke CWRU anterior, la run base queda etiquetada como \texttt{memory\_off} y
la run con Qwen como \texttt{memory\_full}. Los recuerdos citados por
\texttt{structurer} y \texttt{evaluator} pasan el gate sin advertencias. Por
decision metodologica no se implementa todavia memoria consolidada o
reflexiones globales, ya que podrian fijar prematuramente conclusiones y
limitar futuras deliberaciones de los agentes.

Como primer paso hacia una memoria RAG con base vectorial externa se ha
implementado \texttt{QdrantVectorMemoryStore}. Este backend mantiene el mismo
contrato \texttt{VectorMemoryStore} que el indice JSON local, de forma que los
agentes continuan trabajando con \texttt{AgentMemoryQuery} y
\texttt{RetrievedMemoryContext} sin acoplarse al proveedor de almacenamiento.
Cada recuerdo se guarda como punto Qdrant con embedding denso, metadatos
filtrables y el \texttt{ReasoningMemoryRecord} completo en el payload. El
identificador del punto se deriva de \texttt{memory\_record\_id} mediante UUID
determinista, lo que conserva la trazabilidad de upserts y eliminaciones.

La seleccion de backend se centraliza en
\texttt{get\_default\_vector\_memory\_store}: por defecto se mantiene
\texttt{LocalJsonVectorMemoryStore} como baseline reproducible, mientras que
\texttt{TFM\_MEMORY\_BACKEND=qdrant} activa Qdrant con host, clave, timeout y
distancia configurables. Esta decision permite avanzar hacia un RAG industrial
sin perder la capacidad de ejecutar pruebas locales estables ni comparar el
efecto de la memoria contra una linea base. El hito se valida con tests
mockeados de HTTP que cubren insercion, busqueda en coleccion de agente y
memoria compartida, scroll, borrado y seleccion automatica de backend. Quedan
pendientes la migracion JSON--Qdrant, un smoke test con servidor Qdrant real y
la comparacion de retrieval entre ambos backends.

El siguiente hito completa esa primera validacion operacional. Se incorpora el
servicio \texttt{memory\_backend\_migration.py}, que permite migrar registros
entre dos implementaciones de \texttt{VectorMemoryStore} y comparar los IDs
recuperados por ambos backends ante las mismas consultas. La migracion concreta
\texttt{LocalJsonVectorMemoryStore -> QdrantVectorMemoryStore} lee los
\texttt{ReasoningMemoryRecord} ya persistidos, los reindexa en Qdrant y genera
consultas de verificacion por agente y dataset. Para que la comparacion sea
metodologicamente justa, se crea un espejo local temporal reembebido con el
mismo proveedor usado en Qdrant; asi se evita comparar un indice Qdrant nuevo
con vectores JSON antiguos generados por otro modelo de embeddings.

Tambien se anade el script
\texttt{codigo/scripts/migrate\_memory\_to\_qdrant.py} y un servicio Docker
opcional \texttt{qdrant} bajo el profile \texttt{memory-qdrant}. En el smoke
real se levanta Qdrant en \texttt{http://127.0.0.1:6333} y se migra la memoria
existente usando \texttt{local\_hash\_embedding} para aislar la infraestructura
de la disponibilidad de Ollama. El resultado migra 20 recuerdos distribuidos en
\texttt{evaluator\_memory}, \texttt{modeler\_memory} y
\texttt{structurer\_memory}. Las tres consultas de verificacion presentan
solapamiento medio 1.0 y orden exacto 3/3 respecto al espejo local reembebido.
Esto valida que Qdrant puede reproducir el retrieval del baseline bajo el mismo
embedding, aunque todavia queda ejecutar una run agentica real con
\texttt{TFM\_MEMORY\_BACKEND=qdrant} y repetir el flujo con
\texttt{qwen3-embedding:0.6b}.

Como comprobacion posterior, los scripts de ejecucion con memoria se adaptan
para construir el store mediante
\texttt{get\_default\_vector\_memory\_store}. De este modo, una misma run puede
usar memoria JSON o Qdrant modificando \texttt{TFM\_MEMORY\_BACKEND}, sin
cambiar el contrato de los agentes ni el grafo. Se ejecuta un smoke CWRU con
\texttt{TFM\_MEMORY\_BACKEND=qdrant}, \texttt{local\_hash\_embedding} y memoria
de decision desactivada para aislar la infraestructura. La run
\texttt{cwru-memory-qdrant-m4-4-smoke-001} finaliza aprobada y persiste
contextos de memoria para \texttt{structurer}, \texttt{modeler} y
\texttt{evaluator}, todos con
\texttt{retrieval\_backend=qdrant\_vector\_memory\_store}. El benchmark de
efecto de memoria la clasifica como \texttt{retrieval\_only}: Qdrant recupera
memoria y no hay uso invalido, pero al ejecutarse sin LLM no se evalua todavia
la cita ni la influencia deliberativa de Qwen. Esa validacion queda reservada
para una run posterior con agentes LLM y, preferentemente, con el perfil
\texttt{run\_to\_failure\_degradation}.
